# 01 — Product outcomes before features

## Source-backed principle

Jobs to Be Done focuses on the progress someone seeks in a particular circumstance, including functional, social, and emotional dimensions [S06](sources.md#s06). SVPG separates value, usability, feasibility, and business viability risk [S01](sources.md#s01). These lenses help keep a technically interesting idea connected to a useful outcome.

## Boring PM application

Convert “I want an agent for X” into an account of a person, situation, current task, obstacle, and desired change. Let the expert explain their idea briefly, then ask for the incident that motivated it.

Create a one-paragraph problem statement:

> For [specific user], when [situation/trigger], completing [task] is difficult because [supported obstacle]. They currently [workaround]. A useful improvement would let them [observable result], while respecting [important constraint].

Leave unestablished fields explicitly unknown. Keep a proposed feature outside the problem statement so another solution remains possible.

## Separate the roles

| Role | Learn | Common confusion |
| --- | --- | --- |
| Domain expert | How the work and judgments operate | Expertise does not imply representative user behavior |
| User | Real task, environment, abilities, desired result | Usage is not necessarily buying authority |
| Buyer or sponsor | Why adoption is worth funding | Interest is not an actual purchasing commitment |
| Approver | Conditions for permission to operate | Approval does not prove the tool is useful |
| Operator | Support, data, failures, ongoing work | A successful demo does not establish operability |

A person may occupy several roles. For an individual expert's own tool, optimize for their actual use; do not manufacture a market-sizing exercise. For a commercial product, make missing user and buyer evidence visible.

## Establish a measurable outcome

Choose one main outcome tied to the task, such as successful completion with acceptable correctness. Capture the present baseline if available and how it was measured. A target is a product decision, not a fact. Also define a guardrail, such as avoiding an increase in consequential errors or review burden.

Keep three notions distinct: an output (“generated a report”), a user result (“resolved the review”), and a business effect (“reduced support workload”). Do not claim the last from evidence of the first.

## Exit and failure patterns

Exit with an identified first user, one concrete task, a candidate improvement, and the main uncertainty. “Everyone needs this,” “save time,” and “AI-powered dashboard” require further context before they can guide implementation. Use [the brief](../assets/templates/01-brief.md).
