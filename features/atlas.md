# Atlas

The Atlas is one catalogue of every screen and state of an app, shot the same way. It starts with the manifest an app writes (`web/src/atlas.json`), its published JSON schema and the command that checks it, then shoots it. Slice 2 shoots the states; the viewer lands in a later slice of D-1831.

## Sub-features

- `atlas-schema` the manifest format and `boring-ui-blocks atlas <dir> --check [--fixtures <dir>] [--json]`. A state is `id`, `page`, `title`, `given: { fixture, steps? }`, and optionally `flow` and `after` (the label of the arrow that leads to it, only with `flow`); no other field, at either level. `given` is the grammar of an app's `features/examples.json`: `fixture` is a `*.synthetic.*` file of the app's `features/fixtures/` (invented data only), `steps` run in order from `open <screen>`, `upload [<fixture>]` (default `given.fixture`), `click <label>`, `fill <label> <value>` and the atlas-only `wait <text>`; a multi-word label or value is quoted "like this" or « like this ». The schema is `packages/ui/atlas.schema.json` (export `./atlas.schema.json`); the hand-written validator is `packages/ui/bin/boring-ui-blocks.mjs`, dispatched from `packages/ui/bin/boring-ui-blocks.mjs`.
- `atlas-shoot` `boring-ui-blocks atlas <dir> --url <base url> --out <dir> [--fixtures <dir>] [--chromium <path>] [--commit <sha>] [--json]`: runs the check first (same findings, exit 1), then drives a headless Chromium over CDP (Chromium path from `--chromium`, else the `CHROMIUM` env, else exit 2) and shoots every state at 390 (touch, coarse pointer, mobile) and 1280, light and dark, as `<out>/<id>.<390|1280>.<light|dark>.png` (full page), with `<out>/index.json`: `{ version: 1, commit, url, createdAt, states: [{ id, page, title, flow?, after?, shots: [{ viewport, mode, file, sha256, consoleErrors, status }] }] }`. Each state opens `<url><page>`, then runs its `given.steps` in order on the real page with real input; a step waits up to 10 s for its target, and a step that fails stops that state, exits 1 and prints `state <id> step <n> "<step>": <reason>` (n counts from 1; the state keeps `shots: []`). Dark is `prefers-color-scheme: dark` plus the `dark` class on `<html>`; light is the opposite. `consoleErrors` are the console errors and uncaught exceptions of that shot. Every shot runs in its own fresh browser context (no storage, cookies or cache from another shot). `click` lands on the closest actionable ancestor (button, link, role button/tab/…, input, label) of the matched text, and only that element's one accessible name counts, so a `<span>Save</span>` inside `<button aria-label="Delete">` is not `Save`. It picks the first visible, enabled element whose one accessible name (`aria-labelledby`, else `aria-label`, else a label, else its content) equals the label, and waits for a disabled target to become enabled: if it never does the step fails with `element named "X" is disabled` (a native `:disabled` control, so a button in the first `<legend>` of a disabled fieldset is enabled, or any `aria-disabled="true"` ancestor). Every browser request has a bound and each shot a deadline (30 s plus 10 s per step), after which the state fails with `the page did not answer within N s`; Ctrl-C or a kill closes the browser and removes its profile before the process exits (130 or 143). A page taller than 16000 px is cut there: its shot carries `truncated: true` and `height` (the full page height) in `index.json`, and a `warning:` line names the state on stderr.
- `atlas-settle` before each capture the shooter waits until the page has had no request in flight for 300 ms (at most 10 s), then for fonts and two painted frames, so content a page fetches after `load` is on screen and an unchanged state shoots the same on a slow or loaded machine. Drive: the `--since says same for an unchanged state whose content arrives late` case in `test/atlas-shoot.test.mjs` (server holds the fragment 1.2 s).
- `atlas-since` `--since <old index.json>` sets each shot's `status`: `same` when the sha256 matches or fewer than 0.1% of pixels differ by more than 8 in any channel, `changed` otherwise or when the size differs, `new` when the old index lacks that state or shot. Without `--since` every shot is `new`.

## How to get to it (user POV)

- An app writes `web/src/atlas.json` (point `$schema` at `@hachej/boring-ui-kit/atlas.schema.json` for editor help) and runs `npx boring-ui-blocks atlas web/src --check --fixtures features/fixtures`. Each finding prints with its path, such as `states[2].given.steps[0]`; the exit code is 1 on any finding, 0 otherwise.
- To shoot, start the app's preview and run `CHROMIUM=<path> npx boring-ui-blocks atlas web/src --url http://127.0.0.1:4173 --out .cache/atlas --fixtures features/fixtures` (add `--since <previous>/index.json` to mark what changed).

## Driving it with the kit's node tests

Preconditions: Node only for the check (fictional manifests under `test/fixtures/atlas/`); shooting also needs `CHROMIUM` set to a Chromium or chrome-headless-shell binary (CI has it and the test fails, never skips, without it).

- **Schema and check.** `atlas-schema`: `node --test test/atlas.test.mjs` spawns the real bin on a valid manifest (4 states, one flow of 2 with `after`), an unknown verb, a duplicate id, a fixture file the directory lacks, a non-synthetic fixture name, `after` without `flow`, an unbalanced quote and a missing `atlas.json`; it also reads the schema file and requires the validator to agree with it. By hand: `node packages/ui/bin/boring-ui-blocks.mjs atlas test/fixtures/atlas/valid --check --fixtures test/fixtures/atlas/fixtures`.

- **Shoot.** `atlas-shoot`, `atlas-settle` (the late-content case holds the fragment 1.2 s and expects `same`) and `atlas-since`: `node --test test/atlas-shoot.test.mjs` serves the fictional app `test/fixtures/atlas/app/` over http and spawns the real bin: 3 states (a form flow of 2 with `fill`, `click` and `wait`, and an `upload` of a synthetic CSV) give 12 PNGs and an `index.json` with every field; a manifest whose step `click Valider` has no target exits 1 naming the state, the step number and the step text; a page with a `localStorage` write shows nothing of it to the next state, a `click Save` beside a `<button aria-label="Delete">Save</button>` reaches the real Save, a disabled `Valider` (also one inside a disabled button or an `aria-disabled` ancestor) fails the step, a `click Save` on a span inside `<button aria-label="Delete">` finds no element, `click Enable` in the legend of a disabled fieldset works, two Ctrl-C during startup leave no profile and exit 130, a page stuck in `while (true) {}` fails its state by the deadline with no Chromium left; a second run with `--since`, after one page changed, marks only that state `changed`, the others `same` and an added state `new`. `pngChanged` is covered on generated PNGs without a browser.

## Gotchas

- A state is reached by its `given.steps` on the preview's standard fictional seed. A later `--fixture-url` fallback, for data that steps cannot make, will be honoured only on previews and dev identity and refused on live apps; it must never be wired into production. It is not part of this slice.
- Without `--check`, the command needs `--url` and `--out` (else exit 2) and a browser (else exit 2); it never fakes a shot. The bin stays one file with only `node:` imports, so the PNG comparison is inlined (`decodePng` handles 8-bit RGB/RGBA, not interlaced, which is what Chromium writes).
- `--fixtures` is optional: without it, only the `*.synthetic.*` name is checked, not that the file exists.
