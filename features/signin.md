# Sign-in (signin)

An app's sign-in on Better Auth, built directly, with no host around it: the Worker part is the kit subpath `@hachej/boring-ui-kit/signin` (Better Auth, `better-auth`, `@better-auth/core`, `@better-auth/oauth-provider` and `jose` are optional peer dependencies, so an app without sign-in pulls none of them), and the pages are the registry block `sign-in`. One object, `signIn(options)`, answers the sign-in routes of the app's Worker and says who is asking.

## Sub-features

- `signin-invitation` e-mail and password by invitation only: an address not on the app's invitation list is refused with `NOT_INVITED`, in the person's language (`x-boring-lang`, else Accept-Language). The list is a Better Auth plugin table, created with Better Auth's own by the kit's migration at deploy (`signin-migration`). `/api/signin/people` (owners only) lists, invites and removes; a removed person loses access at their next request. `packages/ui/src/signin/auth.ts`, `packages/ui/src/signin/index.ts`.
- `signin-first-owner` the first owner proves a one-use link, never an e-mail: the stack holds the SHA-256 of the link's token (`firstOwnerHash`), a sign-up carrying the token (`x-boring-first-owner`, from `/sign-in?first-owner=<token>`) while no owner exists becomes the owner; once an owner exists the link is dead. The page asks before it shows the owner's sign-up: `GET /api/signin/first-owner` with the token in `x-boring-first-owner` answers `{ valid }` (`true` only while the link's hash matches and no owner exists; one answer, `false`, for a used link, an unknown one and an app with no link), reads only and never uses the link up, so any number of looks leave it good and the first sign-up with it is still the owner.
- `signin-limits` Better Auth's own rate limits, kept in the app's database (every isolate counts the same), with sign-ups per hour per address (20 by default); the person's address is `cf-connecting-ip`. A 429 comes back as a sentence, never a bare status. `packages/ui/src/signin/words.ts`.
- `signin-google` « Continue with Google » when the app has its client (`google: { clientId, clientSecret }`; `/api/signin/options` says `google: true`, the page shows the button): Better Auth's own Google provider, its redirect `<origin>/api/auth/callback/google`. Still by invitation: a Google account gets an account only when its address is invited and Google says it is verified (`email_verified`). The first owner comes by the one-use link, with e-mail and password.
- `signin-mcp-oauth` the OAuth provider an assistant signs in to `/mcp` with: discovery (`/.well-known/oauth-protected-resource/mcp`, `/.well-known/oauth-authorization-server`), dynamic registration (a client whose callbacks are all on loopback is native), PKCE, the « Allow » page; `mcpPerson` reads a bearer token issued for `<origin>/mcp`, `mcpRefusal` is the 401 that sends the assistant to sign in.
- `signin-studio-bridge` Studio's owners are each linked app's owners, proven: Studio signs its owner list by Studio id (`/api/signin/owners`, 5-minute token, its own keys), an owner links an app (`/api/signin/links`, a public PKCE client with no consent screen), and the app's `/api/signin/studio` does the round trip that stores the person's Studio id. Owner in the app = a Studio account whose id is on the current signed list; a direct sign-up with an owner's address never is one. `packages/ui/src/signin/studio.ts`.
- `signin-studio-pass` an app linked to Studio (the `studio` option, plus the optional `studio.owner`) takes Studio's 5-minute pass on `/mcp`, beside its own OAuth tokens, so `app_call` and Studio's assistant reach it as the person: `mcpPerson` checks an EdDSA JWT (issuer `studio.origin`, audience `studio.app`, both exact; at most 300 s long; `sub` and `email` required) against Studio's `/.well-known/jwks.json`, fetched through the link's own `fetch`, kept 5 minutes and fetched again on an unknown `kid` at most every 30 s (a burst makes one fetch), with `jose` and no JWT code of the app's own. The person is the user holding the `studio` account whose `accountId` is the pass's `sub`, else the user of its e-mail when they hold no `studio` account under another `sub`; the role is `roleOf` at this request, never read from the pass (a member's pass is refused where the member's token is; a Studio owner who never made the round trip is a member). It creates no invitation and, with one exception, no user: when `studio.owner` (the creator's Studio `sub`, set at link time) equals a valid pass's `sub`, Studio's signed owner list names that `sub`, and neither the `sub` nor the e-mail is held in the app, the first pass makes the creator's user (the pass's e-mail and `name`, else the e-mail's local part) and `studio` account (`accountId` the `sub`), so they reach `/mcp` with no prior sign-in; a second pass finds them, an existing user is never duplicated nor overwritten, and `studio.owner` unset or empty keeps every pass from making a person. It never stores or logs the pass, and `personOf` never takes it; any key failure (unreachable, 500, no key) or any other pass is the ordinary `mcpRefusal` 401. `packages/ui/src/signin/studio.ts` (`verifyPass`, `StudioClientOptions.owner`), `packages/ui/src/signin/index.ts` (`mcpPerson`, `studioPassPerson`).
- `signin-query-budget` a request costs a few D1 statements and never reads or creates the schema: no `getMigrations` and `advanced.database.validateSchema: false` (on Cloudflare nearly every request is a new isolate, so a per-isolate check still ran almost every time). `makeAuth` also keeps the Better Auth object per isolate and database binding as a saving only (key: the binding as a WeakMap key, then secret, origin, app name, first-owner hash, Google client, Studio link origin/app/client id/owner/TTL, provider flag and sign-up limit; at most 8 per binding; `waitUntil` and Studio's `fetch` read live; the first-owner proof comes from the sign-up's own header). `packages/ui/src/signin/auth.ts`.
- `signin-migration` the tables are the app's deploy step: `@hachej/boring-ui-kit/signin/migration.sql` (`dist/signin/migration.sql`, every statement IF NOT EXISTS) and the `signInMigrationSql` / `signInMigrationStatements()` exports; `applySignInMigration(db)` for deploy scripts and tests. Derived from Better Auth's `getMigrations` by `scripts/signin-migration.mjs --write` (writes `packages/ui/src/signin/migration-sql.ts`); a database with no tables answers 503 `SIGNIN_TABLES_MISSING` with the instruction (`personOf` throws it). `packages/ui/src/signin/migration.ts`.
- `signin-query-budget-test` `@hachej/boring-ui-kit/signin/testing`: `countingD1()` (a fake D1 on `node:sqlite` counting every `prepare().run/all/first/raw`, each `batch` statement and `exec`), `measureSignInQueries({ build, requests = 100, path })` (applies the migration once, signs a fictional first owner up, drives the signed-in requests, each on a fresh isolate and building the sign-in as a Worker does) and `assertSignInQueryBudget({ build, budget = 10 })`, which throws, listing the busiest request's statements, when any request goes over; `resetSignInCaches()` models a new isolate. `packages/ui/src/signin/testing.ts`.
- `signin-pages` the registry block `sign-in`: `SignInPage`, `ConsentPage`, `PeopleList`, `useSignedIn` and `studioNavItem` (the « Studio » entry of an app's left pane, owners only), English and French, labels overridable. `registry/sign-in/`. Made for a phone in any theme: the block's full-width buttons are 48 px high on a phone (the kit's other buttons keep 44), the two switch links take the text colour and are underlined (never `--primary`), the error sits under the form so « Se connecter » stays put, and the people list truncates a long address inside its row so « Retirer » stays in view with no width override from the app. `/sign-in?first-owner=<token>` shows a neutral wait (`sign-in-first-owner-wait`) until the Worker confirms the link; a used or unknown link shows `linkRefused` above the ordinary sign-in form (`sign-in-link-refused`), never « Vous installez … » nor the owner's sign-up. Test ids: `sign-in-submit`, `sign-in-switch`, `sign-in-google`, `sign-in-error`, `people-email`, `people-role`, `people-invite`, `people-row`, `people-remove`, `people-empty`, `people-error`.

## How to get to it (user POV)

- A person opens the app and sees the sign-in page; invited, they create their account; the owner sees « People » to invite others and, in an app linked to Studio, « Studio » to open the app's page there.
- In Claude Code, `claude mcp add --transport http <app> <origin>/mcp`, then the browser opens the app's sign-in and « Allow ».

## Driving it with the example journeys

Preconditions: `npm run build`; no network and no key needed (two Worker instances, a Studio and an app, on in-memory `node:sqlite`).

- **Google.** `signin-google`: `node --test test/packages/signin-google.test.mjs` (a stand-in Google answers the code exchange and its keys in the process: the button only with a client; an uninvited address and an invited one Google does not verify are refused; an invited, verified one gets in as a member).
- **Invitations and the first owner.** `signin-invitation`, `signin-first-owner`, `signin-limits`: `node --test test/packages/signin.test.mjs` (the first test: a stranger refused in French, a guessed and a used link refused, an invited member, a removal); the second: the link's check endpoint, looked at any number of times, one answer for a used and an unknown link, and the first sign-up still the owner.
- **Query budget and migration.** `signin-query-budget`, `signin-query-budget-test`, `signin-migration`: `node --test test/packages/signin-query-budget.test.mjs test/packages/signin-migration.test.mjs` (a hundred signed-in requests, each on a fresh isolate, stay at 10 statements or fewer; an app whose build costs more is refused; a database with no tables answers 503 with the instruction; the shipped SQL equals Better Auth's own for every option set, leaves nothing for `getMigrations` to add, applies twice with no change and the packaged `.sql` equals the string). An app drives it from its own test: `await assertSignInQueryBudget({ build: (database, firstOwnerHash) => signIn({ database, firstOwnerHash, ...the app's own options }) })` (Node 22+ for `node:sqlite`; pass `origin` when the app's build uses another one).
- **Assistant.** `signin-mcp-oauth`: the third test registers a loopback client, runs the authorization with PKCE and opens `/mcp` with the token.
- **Pages on a phone.** `signin-pages`: `CHROMIUM=... node ux/runner/cli.mjs check --target component:sign-in` (the page over a fake Worker, in Coach Max's lime-on-paper theme, light and dark, French and English, at 390 touch and 1440: first visit, the two switch links, a wrong password with « Se connecter » held in place, buttons at least 48 px, the first-owner link used, unknown, good and answered 2 s late) and `--target component:people` (the list in the kit's `Sheet` at 390 with a 40-character address, empty, refused). Set up in `ux/README.md`.
- **Bridge.** `signin-studio-bridge`, `signin-pages` (the `studio` entry in `/api/signin/me`): the fourth test links an app, proves a Studio owner through the round trip, keeps a direct sign-up with an owner's address a member, refuses a Studio member, and drops a removed owner.
- **Studio's pass.** `signin-studio-pass`: `node --test test/packages/signin-studio-pass.test.mjs` (a stand-in Studio serves its keys and signs passes the way `studio/worker/app-token.ts` does; accepted by e-mail and by Studio id, refused for expiry, another `aud` (the other stage's included), an unknown key, another issuer, no account, an invited address with no account, a `sub` mismatch, `alg: none`, HS256, a long pass, missing claims, keys that fail or are empty, and no link; the creator's record: made on a first pass with no prior sign-in (owner-only operation answers as owner, no invitation, one user and one account), not made twice, nor for another `sub` with the creator's e-mail, no `studio.owner`, an invalid pass, a creator Studio does not list, or an e-mail already held; two first passes at once make one; key cache, 30 s refetch and one fetch for a burst of unknown kids; the owner-only stand-in operation; no row, no trace of the pass; and boring-studio's `templates/app/worker/signin.ts`, copied unchanged to `test/fixtures/studio-template-signin.ts`, takes the pass on `/mcp`).

## Gotchas

- Better Auth needs the request's origin: on Workers make one `signIn` per request with `new URL(request.url).origin`. Better Auth's async local storage is per process: two instances in one Node process (tests) must call each other outside it.
- On workers.dev an app's Worker cannot fetch Studio's: give the app's Worker `global_fetch_strictly_public` (or pass a service binding's `fetch` in `studio.fetch`).
- An ID token of Better Auth's provider carries no e-mail: the round trip reads the person's e-mail from Studio's userinfo and checks it names the same Studio id.
- On Workers one `signIn` per request keeps no cache between requests: Studio's pass keys are fetched on each `/mcp` call with a pass unless the app keeps its `signIn` instance (or Studio's `fetch` is a service binding, which is cheap).
- A Studio owner whose address already has a direct account in the app is refused (`account_not_linked`): Studio does not verify e-mail addresses, so the bridge never links by address.
