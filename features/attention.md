# Needs-you blocks

Generic blocks for the "what needs me" surfaces of an app: a waiting question answered in one tap, then the status paragraph and the space card. They take props and call back; the host fetches and posts. Inspired by the Bench patterns (patterns only), built on the style v1 tokens.

## Sub-features

- `inline-question` `InlineQuestion` shows a waiting question where it is mentioned. `kind: 'decision'` is Approve/Refuse for a gate or review; `kind: 'question'` offers up to four choices plus free text (free text only without options) and an optional "Reply in chat". Once `answered` is set it shows the answer instead. A decision calls `onAnswer(id, 'approve' | 'refuse')` (exported as `DECISION_VALUES`): stable values, never the translated button words, so a host never compares labels; an answered decision reads by those values and any other value shows neutrally as "Answered: <value>". `tone` (`'neutral'` default, or `'attention'`): neutral is flat for both kinds (no fill, no padding, foreground text, the question icon, buttons on the surface, the kind label plain small sans text); `attention` is the warning tint with padding and the chip, for gates or critical items only (a decision is warning-tinted too, there is no info tint); the answered state is history, not a card: plain muted text with a check icon and no fill in both tones (attention only keeps its padding); the waiting attention state stays a tinted fill; `className` merges last. `maxOptions` (default 4), `freeText` (false: choices only), `disabled` and `notice` (a line under the controls) let a host such as the chat's `QuestionCard` drive it; the controls carry the test ids `question-option`, `question-input`, `question-submit`. `registry/inline-question/inline-question.tsx`.
- `inline-question-equal-options` (D-1764) the choices of a `question` are all outline buttons: none is primary by position. An option is its text or `{ label, recommended }`; only the first option marked `recommended` is the primary (filled) button; the answer is still the label. A `decision` keeps Approve primary and Refuse secondary. The chat's `ask_user` arguments are plain strings (`packages/agent/src/ask-user.ts`, schema owned here, not by Pi), so a chat question has no marked option today.
- `status-narrative` `StatusNarrative` is the status paragraph: `segments` are text and link parts `{ label, app?, task? }` in order (code-made or model-made text), `at` is the time: a string already formatted by the host is shown as is, a `Date` is shown short in the browser's locale ("6 Nov"; the year is added when it is not the current year) as `<time dateTime title>`; the meta row is sans (D-1742); the root is `bg-card`, `by` the author, `needsYou` the one number of things waiting on the person (tasks waiting + open gates + critical security alerts; hidden at 0), `onOpen(link)` and an optional `onRefresh`. Link parts with `onOpen` are inline text links (an `<a href="#">` with `preventDefault`, so it breaks across lines like text: `text-link`, underlined, no padding or height), exempt from the 44px rule (ruling D-1696); the refresh button keeps it. The theme item defines `--link`. `registry/status-narrative/status-narrative.tsx`.
- `expert-overview` `ExpertOverview` is the page for a person who has little time: under `heading` and `intro`, at most three plain sentences that need them (`needsYou`, the first three of what the app passes; a fourth is not drawn), then « In progress » with one line per app (`apps`), then `done` folded. An item without `later` is one row-wide button named by `action.label` (no gesture word on the row, a caret at its end); an item with `later` shows `action.label` and `later.label` (default « Later ») as two quiet text buttons under the sentence. An app row is a button with a caret only when `onOpen` is given; `unreadable` says `labels.unreadable` in place of `line`, and a row with neither throws. No box, border, badge, count or destructive colour: only a small warning dot. There is no time line; it comes back when measured. `expertOverviewLabels` holds every word the block writes (`inProgress`, `later`, `show`, `hide`, `unreadable`, `calmHeading`, `back`, `progress(reached, total)`), each overridable by key. `registry/expert-overview/expert-overview.tsx`.
- `expert-overview-track` `ExpertTrack` is one app's track: `onBack` (« ‹ <back label> », 44 px), the title and subtitle, the four `steps` in a row (any other length throws naming `steps`) and `note`, then one flat card per feature: `title`, `status` (warning tone only on the person's turn), four segments and `line`, and its `action` when given. Each of the four steps has its own calm colour (info, info and success, success, success and warning: theme tokens, no red), on its segment and its word. Segment `i` is filled in its step's colour when `i < reached`; the segment `reached` is the warning soft tone on the person's turn, muted on the agents' turn, and the border colour when nobody acts (the feature waits). The row says itself too: `aria-label` « <title>: <status>, <labels.progress(reached, 4)> ». Then `done` folded and `extra` as a quiet full-width button. Same file.
- `expert-overview-feature-open` `ExpertFeature.onOpen`: the feature's row opens by tap, Enter or Space. `ExpertTrack` draws the row's title, status, segments and `line` inside one real button (`expert-feature-open`, the whole face, at least 44 px high, the kit Button's focus ring); the feature's `action` stays a second button under it, never nested. Without `onOpen` the row is as before (plain text, only `action` pressable). `registry/expert-overview/expert-overview.tsx`.
- `expert-overview-calm` With `needsYou` empty, `ExpertOverview` shows `calm.heading` (default `labels.calmHeading`, « Nothing needs you ») and `calm.text` in place of `heading` and `intro`, then the apps and `done` as usual. Same file.

## How to get to it (user POV)

- The question appears in a message, a card or a home view. One tap answers a decision or a choice; free text goes with Send. The host posts the answer under the signed-in person's own login, never a shared token.

## Driving it with the render test

Preconditions: `node_modules` installed, so in CI on this VM.

- **Narrative.** `status-narrative`: the same test renders links in order, the time and author, the count pill (hidden at 0 or omitted), French labels, and checks the block reads no clock and never fetches.
- **Question.** `inline-question`: `node --test test/ui/attention-blocks.test.mjs` renders both kinds in both tones (pass `tone: 'attention'` for the tint, omit it for the flat default), free text, the answered states, stable decision values under overridden labels and the four-choice cap, and checks that the block never fetches.
- **Equal options.** `inline-question-equal-options`: `node --test test/ui/inline-question-options.test.mjs` renders the real InlineQuestion with no marker, one marked in the middle, two marked and a decision, and compares which buttons are primary; or pass `options: ['a', { label: 'b', recommended: true }]` in the studio.
- **Expert overview.** `expert-overview`, `expert-overview-track`, `expert-overview-calm`, `expert-overview-feature-open` (a row with `onOpen` is a native button inside the group, the action a sibling, a row without it has none; flow F07 taps it and presses Enter): `node --test test/ui/expert-overview.test.mjs` renders the three states in happy-dom (five items draw three, a question has two buttons and any other row one named by its action, done folds and opens, three or five steps throw, French labels leave no English word); `node ux/runner/cli.mjs check --target component:expert-overview` runs the scenario at 390 and 1440 px, light and dark; the showcase page is « Expert overview ».

## Gotchas

- `ExpertOverview` and `ExpertTrack` take the app's order and cut nothing, but the block shows three items at most and writes no sentence, count or day itself: the app passes every one, in its own words, and the block never builds one (the only words it writes are `expertOverviewLabels`). It shows no count of agent work, by rule; `SpaceCard` is the block that does. A question's « Later » is the app's to act on: it drops the item and the next one moves up.

- The block sends nothing. `onAnswer` is the host's job; keep the question id in the host's closure.
- Store the decision value (`'approve'` or `'refuse'`), not the label; pass it back as `answered`. Labels (`labels`) only change the words.
- Choices beyond four are dropped; a longer list is a form, not an inline question.
- Long replies belong in the chat (`onReplyInChat`); the field here is one line.
- `StatusNarrative` sits on `--card` (`test/ui/surface-cards.test.mjs`). A string `at` reads no clock; a `Date` reads it only to decide on the year (`attention-blocks.test.mjs` counts the reads), follows the browser's locale and timezone, and a server-rendered host should pass a string. Mono is reserved for code and ids: `npm run check` runs `scripts/check-mono.mjs`, which allows `font-mono` only on code, kbd, pre, samp and `data-mono-id` elements. Pass the same `needsYou` number everywhere on a surface; never sum it twice.
- Without `onOpen`, link parts show as plain emphasis.
- In the chat `StatusNarrative` is a host slot (the host supplies the paragraph as the first message through `timeline`, or `belowComposer`); `PiChat` never builds it. The waiting question in the chat is this `InlineQuestion`.
