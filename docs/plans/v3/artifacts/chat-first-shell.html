Chat-first shell: one conversation, one artifact, a Library behind it

The building blocks in packages/workspace are sound. The assembly is wrong: the chat lives inside the dock and every host has to subtract chrome to get a simple app. The fix is a new, thin shell where a Thread chooses its layout: transcript plus one artifact by default, or the app itself full screen with the conversation beside it, over it, or inside it. Today's workspace moves behind a Library entry. No rewrite of the blocks.

Today versus target

Today subtractive

  • WorkspaceAgentFront (2,991 lines) is the app. It owns layout, sessions, plugins, command palette, fleet views and the artifact surface.
  • The chat is a pane inside dockview. The dock is responsible for the whole screen.
  • Two left bars exist: AppLeftPane (990 lines) and WorkbenchLeftPane (372 lines), plus a file-tree rail on the right of the surface.
  • one-chat needs about twenty props and ten display:none rules to hide what it does not want, and still keeps the filesystem plugin registered because it carries the only surface resolver.
  • Every new use case is a new negation prop on the same component.

Target additive

  • A small AppShell: left nav with New chat, Library, and the chat list. Nothing else.
  • Chat route: transcript plus artifact cards. One artifact opens in a viewer beside the chat. Close it and the chat is full width again. No dockview.
  • Library route: today's file tree plus dockview, mounted as a destination. The file tree rail sits on the left, next to the nav.
  • Hosts compose: pick the routes, name the labels, pass the agent. A host like one-chat should be about forty lines.
  • The old front stays as a legacy export until every host has moved.

Mockup

Click an artifact card to open the viewer. Click Library to see the dock. Use the chat switch in the title bar to move the conversation from a column to a floating window to a slot inside the app. The shapes are the deliverable; the styling is placeholder.

An app and its Thread are one whole

In one-chat an app is not a file the conversation produced. The agent, the Thread and the app are one thing with one name in the nav. That changes what "layout" means: it is a property of the Thread, chosen by the app, not a mode of the shell.

In an app layout the agent is just a backend and the chat is just a frontend component. The app is the product. The shell provides both to it and keeps them durable, but the app decides where, and whether, the conversation is visible.

What the shell always owns

  • The nav, the thread list, New thread, Library.
  • The session: transport, streaming, auth, ask_user cards, attention badges.
  • Artifact events and the Library dock.
  • The chat component itself, wherever it is mounted.

What the app decides

  • layout: "thread" | "app". Thread = transcript plus one artifact viewer. App = the app's screen fills the main area as a full-bleed iframe, which is the existing html viewer with its header hidden.
  • chatMount: "column" | "floating" | "in-app". Column beside the screen, a window over it, or a slot the app declares.
  • Both persist on the Thread record, so an app reopens the way it was last used.

Fit with the UI bridge as it exists today

Two bridges, neither reaches the app

  • UI bridge, agent to front. The agent calls exec_ui (openFile, openPanel, openSurface, notify). Commands post to /api/v1/ui/commands, the front long-polls /commands/next and pushes state back to /api/v1/ui/state, which get_ui_state reads.
  • Workspace bridge, front plugin to server. POST /api/v1/workspace-bridge/call with a runtime token. Used by ask-user and bi-dashboard.
  • The app iframe is a dead end. HtmlViewer renders srcDoc under sandbox="allow-scripts …" with no allow-same-origin, so the app runs on an opaque origin. There is no postMessage anywhere in the package. The app cannot talk to the shell and the shell cannot talk to the app.

What the portal needs, and what it reuses

  • Reused as is: exec_ui to open the app full screen (an openSurface on the html artifact with a layout: "app" hint). ui state gains layout and chatMount so the agent knows where the conversation is.
  • New, small: one postMessage protocol between the app iframe and the shell: chat-slot (anchor or rect), chat-slot-resize, and later open-artifact. The parent trusts event.source equal to the viewer's own iframe window, not the origin, because a sandboxed srcDoc has origin "null". No server change, no token, no new route.
  • Alternative with zero new transport: the agent declares the slot at build time with a new exec_ui kind. Static, but enough for a first app. The postMessage route is what makes the slot follow the app's own layout at runtime.
  • Native chat later reuses the workspace bridge token model: the shell hands the iframe a scoped runtime token and the component calls the agent server directly, or every message relays through the shell by postMessage. That is the phase 6 cost, and the current bridge already has the token primitive for it.

Verdict: the portal fits the current setup with one additive piece, an iframe-to-shell postMessage channel. Both server bridges stay as they are.

Viewers are plugin contributions, not a package

A viewer is a panel plus a surface resolver with patterns and a score. Diagram and deck already work this way. The filesystem plugin does not: it bundles seven viewers and the file tree behind one glob table. The split moves the seven viewers into built-in viewer plugins inside the shell package, because artifact cards in every app need them, and leaves the tree with dockview in the Library. The ArtifactViewer and the Library dock ask the same resolver registry with the same open request, so any viewer plugin works in a chat card, in the Library and in an evidence popover without knowing which. The registry already resolves several claims on one target by score, so an opt-in plugin can take over a file type while the code editor stays the fallback. One small addition: a card icon and label per kind, on the resolver's existing metadata.

The chat is a viewer of the Thread

The chat panel is a viewer whose target is a Thread instead of a path. It is already force-registered as a core panel and mounted as a dockview pane by the legacy front; what is missing is that it resolves through the same registry from an open request of kind thread. Then column, floating and in-app stop being chat-specific modes and become placements that work for any viewer, and the iframe portal declares a slot with whatever viewer it wants in it, the Thread viewer or an artifact, through one protocol: slot: { viewer, rect }. Two things stay special and are kept on the Thread adapter, not inside the viewer: only one instance per Thread accepts input at a time, and session lifecycle such as ask_user and attention belongs to the shell.

Consumers keep their import. one-chat without a Library entry never loads dockview. Why not earlier: while the legacy front still imports everything, a split forces the two packages to version in lockstep through the migration. Why the context rule: one-chat's attention context already broke across the package's own bundled entry points and had to be patched with a window-event mirror. A package line is a harder boundary than an entry point.

Fit with the ratified plan: Thread, View, Library

The ratified pack already names the pieces this shell needs. Using its nouns costs nothing now and avoids a second rename later.

What the rulings say

  • Thread is the durable job root with 0..n Sessions (RECONCILIATION §9a, 2026-08-27). One-chat's "app" is a Thread. The nav lists Threads, not sessions.
  • One workbench, many mounts (§8a): the artifact surface is one component mounted inside a Thread as a canvas, under an attention item, as a popover, and standalone as the Library. The ArtifactViewer in the mockup is the "inside a Thread" mount.
  • Library is already the ratified name for the standalone mount, and for the View library once Views exist.
  • Conversation is contextual, beside a View or inside a Thread, never a global assistant pane (§8b). In this shell the chat lives inside the Thread route, so it complies.
  • Chat-first Experience is explicitly valid (§8a scope, 2026-08-27): the five-domain Meridian shell is the flagship, not the only surface. One-chat is the "chat-first expert Agent" case.

How the plan integrates them

  • Name the routes ThreadRoute and LibraryRoute. The nav model is a list of Threads. Until the Thread/Session split lands in the kernel, one Thread maps to one Session behind a small adapter, so nothing is invented in the product layer.
  • Artifact cards list artifacts (files the agent produced), not Views. §8c forbids minting a View descriptor in the product layer before the kernel View contract ships. The viewer takes a path and a kind, nothing more.
  • The Meridian shell later becomes a second preset of the same AppShell: five nav domains instead of two. The Library route is shared as is.
  • The spike at commit 08cc60523 already proved the IA is reachable by recomposing shipped components. This plan is the productised version of that proof.
One tension to rule on: one-chat pins the conversation permanently beside the screen. That is allowed for a chat-first Experience, but the nav must call the items Threads or the host's own word for them, never "sessions", so the later Thread/Session split does not surface in the UI.

Audit evidence

Two code audits, one inside the package and one across every consumer, confirm the hypothesis with one correction: the left bar is a symptom. The disease is a single closed composition root.

Inside the package

  • No slot API. WorkspaceAgentFrontProps has about 95 props. It Omits every layout slot of ChatLayout (nav, center, surface, sidebar, chatPanes) at WorkspaceAgentFront.tsx:234-251, then hardcodes them at :2744-2766. Seven props are typed as public API and never read.
  • Layout is owned in five places with about fifteen localStorage keys and three independent resize-handle implementations. ChatLayout.tsx:566-576 re-opens the chat whenever the workbench closes, which is why chat cannot be hidden.
  • The 2,991-line front is thirteen subsystems, not a composition root: session adaptation, fleet discovery, pane transactions with optimistic-ack windows, four storage schemas with migration, pinning, archive, overlay state machine, imperative surface handle, ui-command stream, warmup gating, palette search, capabilities host, two shell trees. 167 commits in six months.
  • Two layout systems are dead but exported (IdeLayout, buildChatLayout, ResponsiveDockviewShell) while the live, clean slot component PluginTabsWorkspaceShell and the pure-props AppLeftPane are not exported. The default workspaceLayout="classic" is used by no real host.
  • Plugin ids are hardcoded in chrome: "files" pinned and force-selected, "skills" and "plugins" reserved, "agent" in a global shortcut, four core panels registered unconditionally.
  • Good news for phase 0. FileTree is fully standalone. DockviewShell needs only RegistryProvider and one bindStore(), not the whole provider. FileTreeView needs only DataProvider. The surface-resolver indirection is clean.
