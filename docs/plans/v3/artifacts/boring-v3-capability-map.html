boring-ui-v3 · analysis · 18 Sep 2026

A network of self-living apps on a hub, with the agent as a service

v3 is not a rewrite of the workspace. It is a re-centering: apps are the product, the hub runs them, Flue runs the agents, and a small set of platform services is consumed through bindings. Most of what v3 needs already exists, split across three places: boring-hub has the app lifecycle, Flue has the durable agent, and boring-ui-v2 has the auth, payments, sandbox, filesystem and viewer code. What is missing everywhere is the wiring between them. The hub has since grown its own shell, viewers with browser-side tools and ask-user, so the remaining greenfield is smaller than four days ago, and the hub itself is now the reference for how a v3 app looks.

Owner decisions already taken

  • Flue replaces boring-agent's harness layer. Tools, viewers, ask-user and the session UI stay ours. Durable submissions, recovery and the render loop come from Flue. The v2 durable-streams work (P1-A) is superseded.
  • v3 supersedes the v2 ratified pack. Only the nouns survive: Thread, Session, Library, artifact, one workbench many mounts. Plans and sequencing retire with v2.
  • The hub keeps being built in parallel as a standalone, with no auth and no remote sandbox. v3 must consume it, not fork it.
  • Platform shape: bindings first, backends in-process in the standalone hub, extraction later. Decided 18 Sep after the comparison below.
  • Viewer tools: the v2 guardrail is reversed, html/app is the first viewer with tools. The agent patches the app screen directly, which is one-chat's product.
  • The wall comes down by design, not by accident. Apps may trigger the agent and apps may call other apps. That makes the network contract a wave 0 deliverable, alongside the bindings.
  • Secrets: 1Password is the root of trust, the hub store is the per-tenant backend. Recommended after checking the docs, see the open decisions section. Owner ruling pending.
Conflict to record, not to bury. The v2 ratified plan says "No integrating Flue/celld, patterns yes, dependency no" (ARCHITECTURE-PLAN.md line 324), backed by measured evidence: empty process.env under celld and 435 ms cold start. boring-hub has since proven Flue 2.0.8 boots on celld with facets, 37 of 37 hub e2e passing. The decision above supersedes the ruling. It needs one line in DECISIONS.md so rule 11 is honoured rather than skipped.

  • One facet per app with its own SQLite that survives code swaps. Migrations run before current moves.
  • The app contract: default-export fetch(request, env), env.db, x-app-user header. Nothing else.
  • App and profile as two kinds through one path. tools.json mounted into the agent as native tools.

added 19 to 22 Sep, on the ship branch

  • Viewers: file, markdown, tldraw, dashboard, ui-editor, with browser-side tools returning through a read-once result mailbox. ask_user as a compare-and-set row. Attachments, transcription.

  • About 118 test files on node:test. Fitness 29 of 29, agent 61 of 61, app-runner 35 of 35.

lacks

  • CI of any kind. 266 commits exist only on this VM. Eval evidence is gitignored. main is dead since 17 Sep.
  • A boundary between apps: one origin, an editor can reach the owner's other apps and tokens. One role. No console capture.
  • The public authenticated browser path was never verified, and Access's frame policy blocked the app iframe at last record.
  • celld: process.env never populated, bucket production mode never exercised, no Cloudflare deploy ever.

Flue has

  • Durable submissions with exactly one terminal outcome, attempt leases, recovery from durable evidence.
  • Agent as a render function, tools as program logic, MCP connections, sandbox adapters (E2B, Daytona, Modal, Cloudflare, local, virtual).
  • Persistent state per conversation. Canonical append-only records.
  • Inbound channels for a dozen providers, signature-verified.

lacks

  • Any auth or tenancy. A conversation URL is full access.
  • Outbound messaging, app-to-app RPC, a plugin system, secrets beyond env, viewers, ask-user.
  • Durable files: sandbox files are never stored. The hub's "dev filesystem" is a string map in persistent state.
  • Code Mode is a parenthetical in a type file, not a feature.

boring-ui-v2 has

  • Auth with 28 real migrations. Payments with Stripe and Lemon Squeezy, credits, metering, parked but written.
  • The execution stack: SandboxProviderV1, direct, bwrap, node-workspace, leases, and the filesystem HTTP service. About 12k lines, zero imports of the agent.
  • AgentGateway with branded scopes and a conformance suite. The admission shape Flue needs in front of it.
  • Ask-user, automations, tasks, MCP client, governance, secrets crypto, UI bridge, surface resolvers, ui-kit.

lacks

  • Viewers with artifact tools. None expose tools to agents, and a guardrail actively forbids it.
  • Publish, version, undo lifecycle for apps. one-chat hand-built it in skill files.
  • Two live security defects that must not cross: unsandboxed plugin import, and ambient pi auth bypassing BYOK.

What the hub taught in six days

728 commits from 17 to 22 Sep, most on one branch. The verdict from the history: a very good runtime wrapped in a fragile delivery system. v3 takes the runtime primitives wholesale and none of the delivery habits.

Take wholesale

  • Publish implies activate, migrate before switch. A failing migration stores the version and leaves current untouched. The migrations ledger only grows, so undo never destroys data. No preview stage: publish is live, undo is the safety net. Cleanest primitive in the repo.
  • Cells as plugins. "One app cell is one boring plugin." This is the answer to v2's unsandboxed plugin import and to plugins with no per-user data scope.
  • Views as URLs, layouts as pages. Four nouns, View, Viewer, Chat, Layout, and a rule: no layout reaches into a viewer, no viewer assumes a layout. A 250-line layout replaces v2's 2,991-line root. For one-chat the v2 shell is redundant.
  • Identity in one function. Four ordered sources, 401 on null, no default identity.
  • ask_user as a row with compare-and-set. Mechanism, not prose.
  • Deletion as a deliverable. The hub unbuilt about 2,000 lines of its own security theatre once per-app subdomains were dropped.

Do differently

  • Contracts drift in prose within a week. The three-dependency contract held four days, then a fourth binding appeared in the kit README while the API doc still says three. v3's binding contract is a conformance test with a version, never a sentence.
  • Rules do not stop the model, mechanisms do. With a capabilities file in the prompt and a closing reminder, three fresh conversations still leaked provider names. Anything that must not happen gets a refusing tool or a state machine.
  • Render-then-run is a product fact. A tool published in submission N is callable at N+2. Say it in the tool result so the model self-corrects, not in a doc.
  • Name tools so they cannot read as agents. Models called mcp__server__tool through the subagent mechanism. A tool file without frontmatter was silently invisible and the model thrashed for turns. "Got it" without a write call counted as done. Invisible registration must be a loud error.
  • Green unit tests hid two runtime breaks. crypto.randomUUID in an insecure context and raw BEGIN IMMEDIATE on DO SQLite passed 22 of 22 under node:sqlite. Run the conformance suite against the real cell runtime.
  • Delivery discipline. No CI, 266 commits only on this VM, evidence gitignored, two sessions redeploying the same commit to production in parallel, a build step wiping live state twice, secrets printed into a transcript and one not rotated. The process rules were written and then violated. v3 starts with CI and a pushed main on day one.
Two things to close before v3 leans on the hub. The public authenticated browser path has never been verified from outside an SSH tunnel, and at last record Access's frame policy blocked the app iframe for every visitor. And there is no boundary between apps: an editor can publish code that reaches the owner's other apps and tokens. Both are named in the hub's own docs as "must be revisited before real multi-tenant use".

Port order: small parts, fast

Each wave lands in the new repo as an importable piece and is proven by one app on the standalone hub. The app sequence is guestbook, fitness, one-chat, clinic: trivial, then single-user with real data patterns, then the colleague that builds apps, then real health data with uploads and transcription.

0Repo, nouns, contract1 week · gate

Create boring-ui-v3 with the cell binding contract written down first: env.db as today plus env.files, env.secrets, env.sandbox, env.user, env.ask, env.views, each a TypeScript interface with an in-memory reference implementation and a conformance test, in the style of v2's gateway conformance suite.

  • Record the Flue/celld ruling in DECISIONS.md. Record the reversal of the reserved-prefix viewer guardrail.
  • Network contract, decided 18 Sep: env.agent.dispatch(input, idempotencyKey) so an app can start a turn on its own agent, and env.apps.call(address, route, input) under a grant the hub checks. The transport already exists: Flue's router (POST /:id, history, updates, abort) and server-side dispatch. The binding only resolves the conversation for the current user, mints a short-lived token bound to app, user and conversation, the same HMAC pattern as the signed serving URLs, and forwards. Wave 0 designs grants and addressing, not a protocol.
  • Port ui-kit as is. Port the theming tokens.
  • Copy the hub kit into v3 as the app template. The guestbook publishes on the standalone hub from the v3 repo.

Decisions needed before wave 0

  • Tenancy seam on day one. The standalone hub runs without auth, but the AgentGateway funnel sits in front of Flue from wave 2 so nobody builds on "anyone with the URL". Not yet ruled.
  • Secrets backend. Verified against the 1Password docs: vault-per-tenant with a scoped service account per vault is possible, but tokens are immutable at creation, the SDK is Node-only with no isolate path, and the account-wide cap is 50,000 calls per day on Business (10,000 reads and 1,000 writes per hour per token). Their "multi-tenancy" feature is the MSP parent-child model, a different thing. Recommendation: the hub's encrypted SQLite store, using v2's envelope crypto, is what env.secrets reads per tenant; 1Password holds the master key, platform credentials and any tenant-owned service-account tokens. Agent traffic never touches the rate limits, self-hosters need one root secret, and 1Password stays the human vault. Real per-tenant products if ever needed: HashiCorp Vault namespaces or Infisical, both self-hostable.
  • Network grants. With the wall down, who may call whom: an app calling another app acts on behalf of a user, so the grant is the intersection of the user's and the app's. This is the design work the hub docs already named as "the only real design work".

Decided 18 Sep: platform shape (bindings first, in-process), viewer guardrail reversed with html/app first, and the wall comes down by design.

The one-line version. Hub runs apps, Flue runs agents, v2 supplies the services, and v3 is the contract that lets each of them not know about the others. The first real code in v3 is that contract and its conformance suite, then the 12k lines of execution stack that already have no dependency on anything.
