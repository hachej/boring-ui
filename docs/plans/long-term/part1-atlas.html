§0–4One family, three jobs, two dimensions

A purpose-built, sovereign, agent-native application in which humans, Agents, automations, and authorized external clients perform durable domain work through the same governed operations.

There is one foundational product family. Everything else is that family hired for a different job or moved along an independent dimension — never a second architecture. The three jobs:

Job A · scarce: time & throughput

Operate

Normal domain software with an Agent underneath. Humans and Agents share the same governed domain behavior; the app stays visually and operationally primary.

Job B · scarce: expert time & reach

Distribute

An expert's method, Agent, and Experience packaged for other private contexts. Publisher owns methodology and lineage; subscriber owns data, Work, and outcomes.

Job C · scarce: decision quality vs reality

Improve

Candidates compared against incumbents on evidence and real outcomes; revisions promoted or rejected under authority, with rollback always possible.

Cross-cutting consumption modes — how the jobs are reached, not extra jobs:

Channel-first Agent Job Delivery (chat · WhatsApp · email · MCP · API)External / headless machine consumptionBoring's own code factory (orchestrator + workers + review inbox)Developer path — npx boring create → deploy

§2.4 · §5.3 · §5.8The execution spine

The causal chain every unit of customer value moves through. The load-bearing rule: Admission precedes everything billable, and one durable Run identity joins request, authority, cost, effects, artifacts, decisions, and delayed outcomes — the recursive-improvement dataset.

Four moments the platform never conflates

Produceda valid Artifact or result version was created

Acceptedan authorized Human Decision accepted that exact target

§12.4Never collapse — the anti-proliferation pairs

Part 2 must find the fewest identities, but §12.4 names the pairs that may not be merged to shrink the noun count. These are the plan's strongest structural commitments:

Party ≠ Actor

Ownership and liability vs operational identity. The same consultant acts for several customers under different mandates.

Work ≠ Thread ≠ Run ≠ Attempt

Customer value ≠ conversation ≠ admitted execution ≠ worker generation. Each has its own lifecycle.

Package ≠ Version ≠ Release ≠ Deployment ≠ Instance

Lineage, authored definition, verified build, rollout, and owned context never become one mutable "app" record.

Delivery ≠ external Effect

Provider dispatch, confirmed effect, recipient handoff, and acceptance are four different facts.

Evidence ≠ Outcome

"The human liked it" is preference; "conversion rose" is a measured real-world observation under a versioned definition.

Record version ≠ Revision

An ETag is concurrency control. A Revision is an immutable candidate in an incumbent lineage.

Admission snapshot ≠ execution record

Immutable intended context vs append-only actual history. Neither substitutes for audit or observability.

Attention Item ≠ Human Decision

One requests judgment; the other is the typed, append-only response. Timeout never auto-approves.

Usage Fact ≠ price ≠ invoice

Measured consumption is a stable fact; pricing, billing, and settlement are swappable commercial policies above it.

Causal provenance ≠ permission

Knowing where data came from is not the right to export or reuse it. Information-flow policy composes explicitly.

Authentication ≠ Authority

An authenticated Instruction Envelope proves who spoke — it mints no authority and declassifies nothing.

Traces ≠ business audit

Observability references business identities; durable, tamper-evident audit is a separate obligation.

§2.6 · §2.7 · §5.6Trust boundaries, data categories, effects

Five data categories

What data is

Source data (customer/provider-controlled, revocable) · Knowledge (publisher-packaged, versioned) · Memory (scoped personalization, never widens silently) · Evidence (permissioned signals joined to Work) · Operational facts (content-minimized metering/audit). A subscriber fact copied into publisher Knowledge is a privacy incident, not learning.

Six transfer forms

How data crosses

Projection · Artifact · Evidence export · Package · Entitlement · Operational-fact export. Every actual crossing writes a durable Transfer record. A flow that fits no form means the boundary is not trustworthy. Unknown policy combinations fail closed.

Operation kinds + effect dimensions

What actions mean

Compatibility shorthand: observe → compute/simulate → propose → mutate → external-effect. Canonical model: each Operation declares its kind plus all Effect dimensions (mutation, disclosure, delivery, financial, administrative, coordination, external). Approval, retry, autonomy, and audit derive from the full set.

Untrusted content

Data is never authority

Mail, web, uploads, tool output, and child-Agent output carry taint. Conservative Run taint persists across worker replacement; value-level provenance plus typed validation gate consequential sinks. An email saying "send all invoices here" grants nothing.

The ownership boundary, drawn

One Work identity across every channel

§10.6 · §12.7Five golden flows — the acceptance tests

A candidate Part 2 fails if it cannot express all five without parallel object models. Each STRUCTURAL identity must survive at least two materially different journeys:

A — Route-first app & human-only act

  1. Human works in normal Pages under a contract
  2. Agent uses the same delegable Operations
  3. Professional signature stays human-only
  4. Source outage → declared continuity surface
  5. Artifact, Delivery, acceptance, Outcome all separate

B — Channel-first bounded job

  1. WhatsApp message deduped, scanned, Thread-only
  2. Constrained Intake Run clarifies; contract accepted
  3. Fenced Attempts, real model facts, Run taint persists
  4. Effect Group + step-up Approval, atomic consumption
  5. Delivery ≠ dispatch ≠ acknowledgement

C — Package upgrade & sovereign recovery

  1. Release with verified dependency closure
  2. Preflight vs overlays; expand–contract migration
  3. Canary Promotion Plan against Quality Claims
  4. Regional failure → DR plan, identity preserved
  5. EOL/export never gives publisher read-back

D — Factory & protected improvement

  1. Orchestrator delegates narrowing child Work
  2. Platform-recorded gates, not worker self-reports
  3. Assignment & held-out exposure recorded
  4. Immutable Promotion Plan controls canary
  5. Evidence corrections recompute, never erase

E — Cross-party, support & dispute

  1. Mandated collaborator; revocation cascades
  2. Support session: own approval, minimum access
  3. Estimate → usage → invoice → dispute traceable
  4. Suspension preserves data and Level-0 access

§12Part 2 handoff — the nine identity families

Part 2's job: cover the whole space with roughly these durable identity families — or explicitly justify a merge or split. Everything else is a lifecycle record, relation, or extension point:

1 · Party

+ Party Relationship / mandate — who owns, pays, publishes, benefits, bears liability.

2 · Actor & Agent

Operational identity; Agent namespace with fork/derive/revoke lineage, distinct from revisions and runtime.

3 · Instance

Isolated context, exactly one controlling Party; survives provider and runtime changes.

4 · Package → Release → Deployment

Publisher lineage, authored version, verified build, environment rollout — kept distinct.

5 · Source lineage

Connection → Resource → Item → Projection; Capability Providers are separate executable services.

6 · Operation / Domain Contract

Versioned domain semantics, human-only acts, full Effect dimensions.

7 · Work

Durable customer-value lineage independent of Thread, Message, Run, UI, and process.

8 · Artifact

Logical output identity: immutable versions, components, renditions, derivation lineage.

9 · Revision / incumbent

Immutable candidate + active selection; Objective Basis, Evaluator, Promotion Plan attach when improvement exists.

Acceptance test: every applicable BR family maps to named identities, boundaries, lifecycles or extension points, CAP ids, conformance/negative/fault tests, evidence, and an owner — and the final architecture must remain explainable through a small diagram and one named end-to-end Work flow (§12.4 rule 22 — this atlas's spine is a candidate for that diagram).
