One host. One authority.

PR #1038 is not a route rename. It replaces a split runtime architecture with a single CreatedAgentHost that owns Agent lifetimes, sessions, Agent effects, leases, and shutdown—while applications keep policy, product authorization, and app-level filesystem mutations.

01 · Thesis

The change in one sentence

The application decides who may run what and where; AgentHost becomes the only component allowed to turn that policy into a live Agent runtime.

The old system had an AgentHost and compatibility layers that could still assemble routes, resolve runtimes, retain workspaces, and close resources. The new system has one authority exposed through three bounded paths: addressed Agent API/Gateway, app HTTP over Environment leases, and in-process callback leases.

What this buys us

Agent mutations converge on the Gateway, binding/pin rules, durable Agent-effect ledger, and Host lifecycle. Agent reads use addressed binding/pin rules. App filesystem/Git routes and direct Workspace operations instead run through Host-issued Environment leases.

What this document is

An architectural review map, not a line-by-line diff and not a merge sign-off. It explains production behavior and records adversarial findings that still deserve explicit owner disposition.

Owner brief

What must be true before merge

The architecture has converged. The remaining decision is whether its semantics and operational boundaries are acceptable—not whether to preserve a compatibility path.

  1. Close the confirmed defects: malformed attachment bodies must not escape as 500, and unknown Agents must not open dispatcher or app-runtime work before rejection.
  2. Accept or change the persistence contract: production deployments must supply a durable admission ledger; in-memory mode is explicitly test/development-only.
  3. Confirm the session-sharing policy: the implementation isolates by verified workspace/storage scope, not creator user; workspace members can share sessions unless the server derives a per-user namespace or enforces ACLs.
  4. Confirm the access boundary: app filesystem/Git routes stay app-owned but can only obtain Workspace capability through short Host-issued Environment leases.
  5. Confirm the breaking cutover: legacy composition exports and /api/v1/agent/* compatibility routes are intentionally gone.
  6. Verify shutdown under real load: abort, bounded grace, late-publication fences, ledger closure, and lease drain must behave as one lifecycle.

See evidence, status, and merge criteria in the adversarial register →

02 · Shape

Before → after

The large deletion count is the removal of a second composition authority. The large addition count is the complete direct contract required before that second authority could safely disappear.

Before: split authority

  • createAgentHost() existed, but did not own every route and lifecycle edge.
  • createAgentApp(), registerAgentRoutes(), and agentHostLegacyRoute* could independently assemble behavior.
  • Legacy /api/v1/agent/* and addressed routes coexisted.
  • Internal consumers could retain raw Workspace/dispatcher objects.
  • Session operations could lose the Agent owner and rely on “default”.
→

After: direct authority

  • CreatedAgentHost owns fleet, bindings, sessions, effects, leases, and lifecycle.
  • Apps compose direct routes through registerDirectRoutes().
  • Agent routes are exclusively addressed under /api/v1/agents/:agentTypeId/*.
  • Internal access is callback-scoped and revocable.
  • The wire reference is {agentTypeId, sessionId}; authoritative lookup also includes the verified workspace/storage scope.

The migration is deliberately breaking

There is no fallback flag, compatibility alias, or parallel runtime owner. Removed TypeScript exports fail at compile time. Removed /api/v1/agent/* paths return 404; malformed or stale calls to surviving routes receive stable validation/domain errors. Client migration, server contraction, and legacy deletion therefore ship atomically.

04 · Vocabulary

Eight concepts to keep separate

Most review confusion comes from treating “runtime”, “workspace”, “Agent”, and “session” as the same lifetime. They are intentionally different.
Authorized scope
An opaque app-issued capability. AgentHost verifies it and obtains a trusted workspace/actor claim.
Environment
The physical execution placement: Workspace, sandbox/provider, provisioning generation, search/Git/filesystem adapters.
Agent runtime scope
The semantic Agent definition: tools, prompt, Pi resources, session namespace, model/plugin identity, reload digest.
Runtime binding
A published generation combining one Agent type, verified workspace, Environment, semantic identity, harness, and session service.
Session pin
The persisted or inferred runtime-scope identity that prevents an existing transcript from silently moving to an incompatible binding.
Lease
A finite right to use an Environment or binding. It ends at response close, callback completion, abort, drain, or Host close.
Request ledger
A transactional effect record keyed by actor, operation, target, and request ID, with a digest of the intended payload.
Projection
A safe interface over Host authority: addressed HTTP routes, Environment HTTP routes, or callback-scoped in-process dispatch.
05 · Composition

How a live Agent is built

The key interface decision is splitting physical Environment resolution from semantic Agent resolution.

Resolver 1 — Environment policy

resolveAuthorizedEnvironmentScope returns placement identity, workspace root, provisioning fingerprint, optional provisioning, and per-operation filesystem binding resolution. It answers: where can this work run?

Resolver 2 — Agent policy

resolveAuthorizedAgentRuntimeScope returns semantic identity, physical binding slot, session namespace, Pi inputs, tools, prompts, content digest, reload fence, and mutation callback. It answers: what Agent is allowed to run there?

VerifyThe app-issued scope becomes a trusted workspace/actor claim.
Resolve EnvironmentAgentHost checks placement and provisioning compatibility before reuse.
Acquire generationThe Environment manager creates or leases the canonical provider/workspace bundle.
Resolve Agent scopeApp policy supplies tools, prompts, resources, identity, namespace, and reload contract.
Build bindingbuildAgentComposition creates tools → readiness → harness → store → HarnessPiChatService.
Publish currentOne generation becomes canonical for new sessions; pinned older sessions may retain a historical generation.
Why two layers?

Multiple Agent definitions can safely share one expensive sandbox/Workspace generation, while incompatible provisioning never shares by accident. Semantic Agent changes and physical placement changes are no longer conflated. See the concrete identity obligations above before reviewing reuse keys.

06 · Persistence

Sessions are addressed and pinned

A transcript’s wire reference is {agentTypeId, sessionId}. Its authority key is {verifiedWorkspaceStorageScope, agentTypeId, sessionId}, plus a runtime pin. The authenticated subject is verified and attributed on every request, but is not session ownership in the current workspace-shared model.
01

Listing stays storage-first

Once app authorization resolves the permitted session namespace, inventory reads transcript metadata without building an Agent binding or booting a harness. Browsing history should not cold-start Agent compute; authorization may still resolve policy.

02

New session creation resolves current

Creation resolves the current binding for the addressed Agent, persists its runtime-scope identity, and records the addressed reference. This does not imply that an unrelated current generation is silently substituted for an existing pinned session.

03

Existing mutations resolve through the pin

Prompt, follow-up, interrupt, stop, queue clear, rename, delete, attachment, and runtime-capability routes all resolve the exact existing-session binding.

04

Historical bytes are not rewritten

Explicit sessionDir, sessionRoot/sessionNamespace, legacyDefault, CLI defaults, and Core’s sibling /data/pi-sessions inference remain byte/path compatible.

Isolation contract

The addressed Gateway intentionally makes sessions workspace/storage-scope owned, not creator-user owned. Two authorized members of the same workspace scope can address the same session; a different workspace scope receives not-found. If product policy requires private per-user chats, the current default is insufficient: issue a server-derived per-user storage scope/session namespace or add explicit session ACL/owner enforcement. Never trust a client-supplied user or storage key.

Runtime-pin principle

If current configuration no longer matches a pinned session, the system fails closed. It does not guess a migration and does not silently repin the transcript.

07 · Effects

Agent effects use a durable state machine

The SQLite ledger is not chat storage. It owns execution rights and replay semantics for Agent-side mutating operations routed through the Gateway.

Ledger states

pending-admission→ admission-accepted→ in-flight→ completedor rejectedor outcome-unknown
Boundary and deployment contract

The ledger covers Agent-side effects such as prompt, interrupt, stop, queue mutation, reload, delete, and other Gateway mutations. App-owned file/Git HTTP mutations are outside this ledger. Transactional ownership applies only to processes sharing the same SQLite file; unrelated volumes are not a cluster-wide authority. Production must configure durable ledger storage. In-memory fallback is test/development compatibility, not a safe production topology.

08 · Reload

Reload is compatible mutation, not replacement

The reload path is strict because a mutable plugin tree and a durable request ledger must agree on exactly what was authorized.
Snapshot identityResolve semantic identity, physical binding identity, provisioning fingerprint, and content digest without mutating.
Claim requestThe ledger owns the reload before effects begin.
Compare currentIdentity/fingerprint/physical-slot changes return AGENT_RUNTIME_RESTART_REQUIRED.
Check pinA session pinned to a retired generation cannot reload the current generation through a side door.
Revalidate bytesPi settings, prompts, skills, packages, and extension artifacts are bounded, contained, content-hashed inputs.
Apply mutationPlugin/backend resources update under a binding fence, followed by harness reload.
Revalidate againDrift after admission cannot publish a clean success receipt.
Important tradeoff

Reload is not a transactional hot-swap with rollback. Compatible resources mutate in place. Identity, placement, binding-slot, or provisioning changes are immutable through reload and return AGENT_RUNTIME_RESTART_REQUIRED; the app must replace/restart the binding through lifecycle policy. If failure occurs after mutation begins, the request may become outcome-unknown and requires operator judgment rather than blind replay.

09 · Lifetime

Capabilities are finite

The cutover replaces retained raw Workspace/dispatcher objects with leases whose end can be enforced.

Environment HTTP lease

Files, tree, search, Git, share, and FS-event routes borrow an Environment after app authorization. Normal requests release on response/error. Streaming routes keep the lease until request abort, socket close, or response transport close.

Callback-scoped Agent lease

runWithWorkspaceAgent(input, callback) supplies guarded Workspace access, AbortSignal, dispatch, interrupt, and stop. Outstanding work is tracked. On callback completion or shutdown, the projection is revoked and late operations/results are fenced.

Drain then close

Fastify preClose drains; onClose closes. The Host stops acquisition, aborts cooperative operations, waits a bounded grace period, fences late publication, closes connections/bindings/Environments, and tears down ledger/provider resources through idempotent close guards.

Bounded does not mean magical cancellation

A provider promise that ignores AbortSignal cannot be physically rolled back. The Host guarantees that its late result cannot republish into a retired generation.

Why attachments changed

Attachment reads now resolve the exact existing-session binding first. They no longer reconstruct a “current” runtime after authorization, which could read bytes through a different generation than the transcript that referenced them. Upload paths are bounded by count and byte limits, and malformed payloads should produce stable 4xx errors—one reviewed branch currently needs correction; see §17.

Readiness and errors are contracts

Readiness is an Agent-addressed lease whose SSE lifetime ends on request abort, socket close, or response close. Validation, unknown-Agent, session-pin, restart-required, and shutdown failures use stable error codes so clients do not infer semantics from message text.

13 · Integrations

Downstream behavior changes

Integrations were migrated because direct Host ownership is only real if background and plugin paths cannot bypass it.
Boring Automation

Manual and due runs require a host-selected Agent, persist addressed session/dispatch state, and perform workspace-backed store operations inside a Host callback lease. This removes direct retention of raw dispatchers and aligns recovery with the durable Agent effect model.

Managed Agent MCP

The full app rechecks configured workspace membership and performs dispatch, stop, and artifact reads inside runWithWorkspaceAgent. Adversarial review notes that the current implementation buffers events until dispatch completes rather than yielding progress incrementally; see the risk register.

Live transcription

Recording owns an Environment/Agent lease for the transcript lifetime and releases on terminal state. Adversarial review flags that the direct CLI path may not wire the prior Agent review broker; this needs explicit product disposition.

Ask User, Tasks, CCUsage, GitHub PR Tracker

Frontends and helper actions now carry agentTypeId, create addressed sessions, and send addressed prompts. Their visual/product behavior is mostly unchanged; the important change is identity propagation.

16 · Adversarial review

Merge findings, classified

This register separates defects confirmed in the reviewed head from conditional hazards and owner decisions. Architecture claims are not substitutes for disposition.

Confirmed defect Fix before merge

P1
Malformed attachment bodies can become 500
resolveAttachments throws before the prompt route enters its try/catch; the global error handler then emits an internal error instead of a stable 4xx validation response. Evidence: httpProjection.ts L264–273, L492–497, L1089–1099.Merge criterion: malformed attachment arrays and entries return the documented stable 4xx code, with regression coverage.
P1
Unknown Agents can open runtime resources before rejection
Dispatcher and Environment setup can occur before the fleet-membership check rejects an unknown agentTypeId. This violates the intended “authorize before expensive work” boundary even if the request ultimately fails. Evidence: createAgentHost.ts L802–819, L1005–1019.Merge criterion: fleet membership is checked before dispatcher, Environment, or Agent-runtime acquisition.

Conditional hazard Prove the deployment invariant or change code

P1
SQLite and session serialization are not distributed locks
Ledger ownership is transactional only for processes sharing one SQLite file; per-session serialization is process-local. Correctness therefore depends on one Host writer per namespace and sticky/shared storage placement.Merge criterion: production topology and rollback runbook explicitly enforce one writer and a durable shared ledger boundary.
P2
Long-lived caches need bounded operational assumptions
Published bindings and compatible Environment generations can live until Host close. High-cardinality multi-workspace processes should prove bounded identity churn or define retirement/eviction.Merge criterion: accept a bounded deployment assumption or add observability and retirement policy.
P2
Shared reload resources need a concurrency proof
Binding-local reload fences are safe only if mutable resources are binding-local. If multiple Agent types share a mutable workspace/plugin registry, concurrency requires an Environment-level fence or an explicit immutability argument.Merge criterion: trace ownership of every mutated reload resource and document or enforce the correct lock scope.

Owner decision Accept the product/operations tradeoff explicitly

D1
Durable ledger is mandatory in production
In-memory mode cannot survive crash or coordinate writers. It remains useful for hermetic tests and local development only.Decision: require durable configuration in production startup and monitoring, or reject the current deployment contract.
D2
No compatibility window
Old imports and /api/v1/agent/* callers fail immediately. Atomic migration is simpler and safer internally, but demands coordinated rollout of every client.Decision: approve the breaking cutover and verified consumer inventory; do not add a dual-authority fallback.
D3
Ambiguous provider completion is operator work
A reload/effect that mutates externally and loses confirmation becomes outcome-unknown. The system intentionally refuses blind replay rather than promising impossible exactly-once semantics.Decision: accept the operator reconciliation path and define its runbook/telemetry.
D4
Sessions are workspace-shared, not user-private
The Gateway uses authSubjectId for authorization, attribution, runtime inputs, and ledger ownership, but deliberately omits it from addressed session ownership. A second authorized subject in the same workspace scope can connect to the creator’s session; the isolation test encodes this behavior. Evidence: harnessPiChatService.ts L1127–1138, sessionIsolation.test.ts L23–44.Decision: explicitly approve collaborative workspace sessions, or require server-derived per-user partitioning/session ACLs before merge.

18 · Reading path

A practical review order

Do not review alphabetically. Follow authority from contract → lifecycle → effects → projections → app policy → clients.
01 Ownership contracts 02 Registry and lifecycle 03 Environment generations 04 Binding construction 05 Sessions and effects 06 Durable ownership 07 Addressed HTTP 08 Reload and capabilities 09 In-process leases 10 Richest app composition 11 Hosted authorization 12 Client contract

Stop points by concern

  • Identity: after steps 01–05, prove workspace, actor, Environment placement, binding slot, semantic identity, and session namespace cannot collapse into one another.
  • Effects: after steps 05–06, trace duplicate request IDs, digest conflicts, retryable admission, crash/nonterminal state, and outcome-unknown.
  • HTTP: after steps 07–08, trace malformed input, unknown Agent, attachment limits, readiness disconnect, pin mismatch, and restart-required errors.
  • Lifecycle: after steps 02–03 and 09, simulate request close, callback return, abort-ignoring providers, drain, and repeated close.
  • App boundaries: at steps 10–11, verify authorization precedes Host acquisition and app filesystem/Git mutations do not masquerade as ledger-owned Agent effects.
Review outcome to seek

You should be able to answer four questions: Who authorizes? Who creates? Who may retain? Who closes? If any production path has two answers, the cutover is incomplete.
