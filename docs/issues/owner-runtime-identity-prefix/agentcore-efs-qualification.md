# ECS-local / AgentCore shared-EFS qualification

Status: **deterministic host-contract coverage only; live AWS unverified**. No AWS credentials or disposable AgentCore/EFS infrastructure were available for this slice. The tests do not establish AWS service semantics, IAM, network isolation, encryption, or durability.

## Host fixture

`apps/factory-playground/src/server/agentcoreEfsRuntime.ts` defines two application-owned names (`factory:ecs-local-efs` and `factory:agentcore-remote-efs`) with `createProviderRuntimeModeAdapter`. They are deliberately absent from builtin IDs and auto detection. Factory's production composition root accepts a host-only `runtimeModeAdapter`; browser and Agent input cannot select it. The application must supply an authenticated `AgentCoreRuntimeClient` and a `PostgresFencedSandboxHandleStore`; the adapter has no AWS SDK dependency.

The EFS access point must expose `<accessPointRoot>/<tenantId>/<workspaceId>` to ECS. AgentCore must mount that exact namespace at `<runtimeRoot>/<tenantId>/<workspaceId>`. Before acquiring a remote lease, the adapter lexically canonicalizes the host and POSIX roots, performs `lstat` and `realpath` checks over the existing access-point/tenant/workspace components, rejects symlinks, and verifies the canonical workspace remains beneath the canonical access-point root. AgentCore-reported and per-exec cwd values must be canonical POSIX absolute paths contained by `posix.relative`.

These filesystem checks are intentionally fail-closed but inherently TOCTOU-prone: namespace entries can change after inspection. They are defense in depth, not production confinement. EFS access-point identity/root isolation and IAM are the production authority. The host must not expose a broader mount or rely on string/path preflight as a substitute.

The remote pair owns an `active → disposing → disposed` lifecycle. Fence renewals are serialized and each remote create, resume, exec, or delete is preceded by a fresh database renewal with enough confirmed lease validity. A separate timer aborts at the last database-confirmed deadline even when renewal is stalled; no provider call starts after that deadline. Fence loss aborts in-flight work and blocks new calls; disposal aborts and drains calls before releasing its lease.

A newly created opaque handle is encrypted and persisted as `pending-validation`. Only after provider metadata validation does a current fenced database mutation atomically mark it `published`. A successor never resumes a pending handle: it reconciles deletion under its own current lease, retaining pending state and cleanup outcome as durable debt after failed or ambiguous cleanup. Cleanup stops issuing follow-up mutations after fence loss. Normal disposal releases ownership only—it never deletes a published AgentCore session or any EFS data.

## Deterministic qualification

`apps/factory-playground/src/server/agentcoreEfsRuntime.test.ts` runs the canonical `providerPairConformance` suite against both the ECS-local-EFS and AgentCore-remote-EFS provider wrappers. It also exercises both adapters against the same host namespace and compares a real SHA-256, while explicitly remaining a fake-provider test. Coverage includes canonical cwd rejection, traversal and duplicate separators, pre-aborted execution, symlink preflight before acquisition, distinct workspace keys, restart/resume reconstruction, serialized renewal and hard-deadline fence loss, in-flight draining, retryable shared disposal, durable pending-validation cleanup, and a delayed-delete/takeover race proving a predecessor cannot tombstone successor cleanup. A real-Postgres regression stalls the old owner's renewal through expiry, performs takeover through an independent connection/store, and proves the stale exec never reaches the client. Core's `PostgresFencedSandboxHandleStore.test.ts` separately exercises the real Postgres implementation with encrypted pending/published state, independent discriminator keys, stale fences, renewal loss, and failed/ambiguous cleanup-only debt that blocks duplicate create/publish while allowing current-fence deletion retry. Neither suite is a live AgentCore claim.
