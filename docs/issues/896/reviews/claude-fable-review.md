# Final architecture review — gh-896 plan (host-worker intent)

**Verdict: CLEAN.** No blockers. The plan is implementable, minimal for its goal, secure enough for the trusted-plugin threat model, and consistent with the AgentHost/Fastify lifecycle and Automation resource ownership as they exist in this worktree.

## What I verified independently against code

I did not take rounds 1–5 on faith; every load-bearing claim checks out in the current source:

- **The problem is real and accurately described.** `plugins/boring-automation/src/server/index.ts:91-112` today has three overlapping owners: a route `onClose` closing the event bus, route `onReady`/`onClose` hooks starting/stopping the scheduler, and a `shutdown` participant on the plugin object. The plan's "split ownership, duplicate stop paths" framing is correct.
- **Projection mapping conflict exists and the plan resolves it.** The addressed projection runs full `host.drain()` in `preClose` (`packages/agent/src/server/agent-host/httpProjection.ts:402`), while the legacy path splits begin/drain across hooks with per-projection error aggregation (`createAgentHost.ts:476-525`). Decision 4 pins one error-safe mapping (`onListen → startWorkers`, `preClose → beginDrain`, `onClose → close` with implicit drain) and explicitly retires the drain-in-preClose call. The `close()`-implicitly-drains design cleanly resolves round 3's skip-close-on-rejecting-drain hazard.
- **Trust enforcement is implementable exactly as written.** `assertWorkspaceBridgeHandlersTrusted` already exists entry-bound in `pluginEntryResolver.ts:160-172`, and both resolution loops call it while `entry` is still in scope (`createWorkspaceAgentServer.ts:814`, `createCoreWorkspaceAgentServer.ts:998`) — before provenance is erased. Generalizing it to cover `hostWorkers` is a local change. The "hotReload is not authority" wording correctly admits both real default shapes: Core uses `{ hotReload: false, trust: 'internal' }`, standalone Workspace uses `{ hotReload: true, trust: 'internal' }`.
- **The lifecycle error claims are grounded.** The uncoded `TypeError('legacy route lifecycle already registered')` at `createAgentHost.ts:531` exists; replacing it with coded `AGENT_HOST_LIFECYCLE_CONFLICT` is correct. `registerLifecycle` at mount time gives Host a concrete single registration point.
- **Scheduler adaptation is feasible without weakening guarantees.** `HostedAutomationScheduler` already exposes `beginShutdown`/`drain`/`stop`, no-overlap via `activeTick`, and Croner `unref`/`protect` (`hostedScheduler.ts:27-58,87-93`) — the Decision 11 preservation list maps onto existing mechanics rather than requiring a rewrite.
- **Event-bus ownership fix matches the code shape.** `defaultBoringAutomationServerPlugin` constructs the Postgres bus and passes it inward as `options.eventBus` (`index.ts:140,147`), so ownership genuinely cannot be inferred from presence — the explicit `eventBusOwner` marker is the right call, and "in-memory close may remain a no-op" keeps the caller-created in-memory path harmless.
- **Proof commands are executable.** Both files named in the `hostWorkers` guard exist (`agentHostLegacyRouteOptions.ts`, and `shutdown.ts` for deletion), the guards are fail-on-match, the issue-history exclusion resolves the self-matching problem round 4 caught, and Core's 30-second outer deadline is real (`SHUTDOWN_GRACE_MS = 30_000` in `createCoreApp.ts:23`).
- **Security posture is proportionate.** Workers get only `AbortSignal` + logger; actor verification stays per-candidate in `HostedDueRunService`; no long-lived actor capability enters the worker; capability expansion is explicitly out of scope. For an in-process trusted-plugin model this is least-authority done sensibly, not sandbox theater.

The five review rounds converged monotonically — each round's required revisions are verifiably present in the current plan text (onListen placement, provenance-before-bootstrap, non-throwing abort listeners, SSE proof correction, frozen API, uniform startup-failure policy, coded terminal errors, trust-test wording, executable guards, aligned Problem ordering). I found no contradiction that survived into the final text.

## Non-blocking improvements (optional, do not gate implementation)

1. **Specify `AgentHostWorkerLogger`'s method set** (presumably `debug/info/warn/error` mirroring the scheduler's `SchedulerLogger`) so Slice 1 doesn't guess and Slice 2 doesn't adapt.
2. **State `startWorkers` behavior from post-`created` states explicitly** — the plan says repeated calls are no-ops and start-after-abort must not occur; one sentence saying "startWorkers in `aborting`/`drained`/`closed` is a no-op" (vs. a coded error) removes the last micro-ambiguity.
3. **Diagnostic austerity trade-off**: retained/normalized worker errors omit cause, message, and stack by design. Automation logs internally, so it's fine here, but a future worker author who only throws will get worker-id-only diagnostics. Worth one sentence in `PLUGIN_SYSTEM.md` telling worker authors to log before rejecting.
4. **Scheduler-disabled resource-owner worker**: Decision 9 implies Automation contributes a worker even when `hostedSchedulerEnabled` is false (solely to hold and close the composition-owned bus). The tests cover it, but naming that pattern explicitly in the Automation Files section would prevent an implementer from gating the entire `hostWorkers` contribution on `hostedSchedulerEnabled`.
