## Review

- Correct: The plan identifies the real duplication in PR #906: Automation currently starts/stops the scheduler in route hooks while also exporting a shutdown participant (`plugins/boring-automation/src/server/index.ts:76-113`), and Agent has separate participant loops in both legacy projection and standalone app paths (`packages/agent/src/server/agent-host/createAgentHost.ts:473-525`, `packages/agent/src/server/createAgentApp.ts:173-190,365-387`). A lifetime promise plus cancellation signal is a materially better join contract than another `begin`/`drain` rename.
- Correct: Once-per-Host cardinality fits the current composition. Core constructs one Host before registering all plugin routes (`packages/core/src/app/server/createCoreWorkspaceAgentServer.ts:1163-1190,1279-1295`), while Automation already shares one `HostedDueCoordinator` between timer and endpoint (`plugins/boring-automation/src/server/index.ts:57-60,86-99`).
- Correct: The required tick/resource order is right: stop Cron admission, join `activeTick`, then close the event bus. The current scheduler exposes exactly those mechanics (`plugins/boring-automation/src/server/hostedScheduler.ts:27-58`), and the plan correctly removes route ownership of scheduler startup.
- Correct: The plan preserves the existing request-free dispatcher and per-candidate actor verification rather than granting workers raw Host/Gateway authority (`docs/issues/896/plan.md:113-130`). That is the correct trust boundary for this refactor.

### Prioritized blockers and required plan revisions

1. **Blocker (P0) — The promised readiness-failure cleanup cannot be implemented with the proposed `onReady` placement.**
   - Plan conflict: workers start in Fastify `onReady` (`docs/issues/896/plan.md:76-95`), yet the plan promises that a later readiness failure aborts and joins already-started workers (`docs/issues/896/plan.md:140-146`) and requires that test (`docs/issues/896/plan.md:249-264`).
   - Grounding: Agent projection is registered before UI and plugin route children (`packages/core/src/app/server/createCoreWorkspaceAgentServer.ts:1279-1295`). Fastify traverses later plugin `onReady` hooks after earlier children. A later hook failure rejects `app.ready()` but does not invoke `onClose`; the runtime probe returned `{"message":"late-ready-failure","started":true,"closed":false}` and only changed `closed` after an explicit `app.close()`. The Host cannot observe or clean up a readiness error raised by a later Fastify plugin.
   - **Exact revision:** Start process workers from Fastify `onListen`, not `onReady`. Define startup as “once, after readiness has completed successfully and the server begins listening.” Change the immediate-start test to use `app.listen()`. Change “partial readiness failure aborts started workers” to “readiness failure starts no worker,” and retain a separate test that explicit `app.close()` after any failed/partial app construction is idempotent. If non-listening/injected apps genuinely need workers, define an explicit composition-root start call; do not claim `onReady` can provide global last-hook semantics.

2. **Blocker (P0) — Trust cannot be enforced in `bootstrapServer` after provenance has been erased, and the stated policy excludes the actual Automation delivery path.**
   - Plan conflict: only app/prebuilt plugins may contribute workers and directory/hot-loaded plugins must be denied (`docs/issues/896/plan.md:103-111`), while `bootstrapServer` is assigned trust validation (`docs/issues/896/plan.md:213-222`).
   - Grounding: `bootstrapServer` receives bare `WorkspaceServerPlugin[]`, with no entry provenance (`packages/workspace/src/server/plugins/bootstrapServer.ts:22-26,59-70`). Trust currently exists on `DirPluginEntry`, and privileged bridge contributions are checked before provenance is dropped (`packages/workspace/src/app/server/pluginEntryResolver.ts:149-171`). Full-app Automation is a default package resolved as a trusted directory entry (`packages/core/src/app/server/createCoreWorkspaceAgentServer.ts:930-999`), and standalone Workspace defaults are trusted directory entries with `hotReload: true` even though activation remains boot-time (`packages/workspace/src/app/server/createWorkspaceAgentServer.ts:790-821`). The literal proposed policy would reject Automation or incorrectly equate diagnostic re-import with live activation.
   - **Exact revision:** Generalize `assertWorkspaceBridgeHandlersTrusted` into an entry-bound `assertPrivilegedHostContributionsTrusted(plugin, entry)` and call it in both Workspace and Core resolution loops before stripping `entry`. Permit prebuilt app plugins and directory entries explicitly marked `trust: "internal"`; reject untrusted directory entries. State that `hotReload` import mode is not authority—workers are captured once at boot and never replaced by reload diagnostics. Add `packages/workspace/src/app/server/pluginEntryResolver.ts` and both resolution loops to “Files and Responsibilities.” Make `bootstrapServer` validate shape/IDs and namespace already-admitted workers, not infer provenance it does not have. Put trust tests at the resolver/composition boundary, not only at `bootstrapServer`.

3. **Blocker (P0) — “Abort listener throws” is not containable with native `AbortSignal`, so the failure policy is impossible as written.**
   - Plan conflict: the host must abort every worker even if an abort listener throws and worker failure must not crash the process (`docs/issues/896/plan.md:49-58,138-153`).
   - Verified runtime behavior: `AbortController.abort()` returned normally, then Node surfaced the listener exception through `uncaughtException` on a later turn (`abort-returned`, then `uncaught listener boom`). A `try/catch` around `abort()` cannot contain it.
   - **Exact revision:** Add a worker conformance rule that abort listeners **must not throw** and remove the containment promise/test for thrown native listeners. The Host should still own one controller per worker and call every controller’s `abort()` before joining. If containment of arbitrary cancellation callbacks is non-negotiable, replace `AbortSignal` with a host-invoked callback protocol; that is a larger API and should not be smuggled into this slice. Also specify that synchronous `run()` throws and promise rejections are normalized to a safe `AgentHostWorkerError` carrying stable code and final worker ID; logs must omit raw error message/stack because the plan promises diagnostics do not leak secrets (`docs/issues/896/plan.md:103-105`).

4. **Blocker (P0) — Automation resource ownership and the shutdown SSE proof are mutually inconsistent.**
   - Plan conflict: the worker exclusively owns event-bus disposal, including scheduler-disabled mode, while direct route mounting remains supported as route-only (`docs/issues/896/plan.md:132-136`); the manual proof also expects the final draining tick’s invalidation to arrive over the existing SSE connection (`docs/issues/896/plan.md:331-338`).
   - Grounding: the SSE response is a hijacked long-lived route (`plugins/boring-automation/src/server/routes.ts:31-73`). Fastify closes that stream before `onClose`; the runtime probe held an `onClose` gate and observed the SSE reader return `{done:true}` while the gate was still blocked. Worker join/disposal is intentionally deferred until `onClose`, so a final tick completed there cannot notify that same connection. Separately, removing route `onClose` from `plugins/boring-automation/src/server/index.ts:91-100` leaves direct mounting with no owner to close a caller-supplied/Postgres event bus. Keeping both closes would recreate duplicate ownership and, because plugin routes register after Agent routes, could close the bus before the worker’s final tick.
   - **Exact revision:** Declare `automationRoutes` a borrower: it never starts or closes the event bus. Full plugin/Host composition owns an internally-created bus through the worker lifetime; direct route tests/callers must inject and close their own bus, and direct mounting of the hosted default plugin is unsupported. In the worker, require `try/finally`: stop Cron admission, join the active tick, then close the bus exactly once even after startup/tick failure. Replace the shutdown proof’s “SSE receives the terminal invalidation” with: the open SSE stream terminates promptly during Fastify close, the final tick reaches durable terminal state, and reconnect/read-after-restart observes that state. Add a real-listener test that `app.close()` with an open Automation SSE stream settles and unsubscribes.

5. **Blocker (P1) — The public lifecycle/state machine leaves ownership and failure transitions underspecified.**
   - Plan ambiguity: lifecycle methods are “added if needed” (`docs/issues/896/plan.md:201-205`), `close` allegedly completes binding/resource cleanup, and all projections should only call common Host methods (`docs/issues/896/plan.md:76-101`). But the legacy binding lifecycle is currently projection-owned and must stop admission before Host runtime drain (`packages/agent/src/server/agent-host/createAgentHost.ts:475-535`; the registered binding lifecycle originates in `packages/agent/src/server/agentHostLegacyRouteRuntime.ts:280-291`). The diagram also permits direct `created -> closed` while the rules say `close` implicitly drains (`docs/issues/896/plan.md:174-195`). It does not say what state is reached when worker join or runtime drain rejects, or whether later `close()` retries cleanup.
   - **Exact revision:** Freeze the API in the plan: `CreateAgentHostOptions.hostWorkers`, plus `AgentHostHandle.startWorkers`, `beginDrain`, `drain`, and `close`; no worker fields on HTTP projection options. Define transitions as `created -> running -> aborting -> drained -> closed` and `created -> aborting -> drained -> closed`; no direct bypass. State advances to `drained`/`closed` after all corresponding cleanup attempts even when the returned promise rejects. `drain()` must: abort workers; `allSettled` every started lifetime; synchronously close legacy binding admission; drain Host runtime effects; then reject with the first normalized failure. `close()` must await/capture `drain`, close legacy bindings and remaining runtime resources regardless of that error, set `closed`, then reject with the retained first failure. Register the internal legacy projection lifecycle into Host at mount time so the Host can enforce that order without exposing plugin shutdown callbacks. Add tests for binding admission during worker drain, closure immediately before runtime drain, and cleanup after a worker rejection.

6. **Note (P1, scope) — This is the maximum defensible scope; remove speculative material rather than broadening it further.**
   - PR #906 already changes 70 files and the plan adds a new exported cross-package lifecycle primitive for one consumer. The abstraction is defensible only if it remains a Host lifetime/join mechanism. The future capability design at `docs/issues/896/plan.md:117-126` is not actionable for this change and distracts from the security contract.
   - **Exact revision:** Collapse Decision 7 to one sentence (“workers receive cancellation and logging only; Automation continues to use its existing trusted dispatcher closure”) and move all hypothetical capability-grant bullets to Out of Scope or a follow-up issue. Do not add restart, health, worker status APIs, fleet selection, or schema changes. Name the API now (`hostWorkers` / `AgentHostWorkerIntent`) and delete Open Question 1 before marking the plan ready for implementation.

### Additional required plan edits

- Resolve Open Questions 2–4 instead of shipping them into implementation (`docs/issues/896/plan.md:383-388`): retain “log/no restart,” but define shutdown rejection behavior; adopt the explicit direct-mount ownership rule above; and cite Core’s actual 30-second outer deadline (`packages/core/src/server/app/createCoreApp.ts:23,72-155`) while noting non-Core embeddings have no such process deadline.
- Replace “invalid/non-lifetime declarations fail validation” (`docs/issues/896/plan.md:266-275`) with what can actually be validated: array/object shape, safe local ID, callable `run`, duplicate final ID, and thenable return at invocation. “Remains pending until abort” is behavioral and can only be contract-tested, not boot-validated.
- Give the PostgreSQL proof an exact command and prerequisite instead of “use the existing command” (`docs/issues/896/plan.md:329`). The current Automation package has only `test`; its migrations test defaults to `postgres://ubuntu:test@localhost/boring_ui_test` (`plugins/boring-automation/src/server/__tests__/migrations.test.ts:7`).
- Add a source search for the new duplicate owner paths too: no Automation scheduler `onReady`/`onClose`, no plugin route event-bus close, and no worker arrays on HTTP projection options.

**Verdict: NOT CLEAN.** The lifetime-worker direction is sound, but readiness semantics, provenance enforcement, native abort failure claims, HTTP/SSE resource behavior, and Host/binding state ownership must be revised before the plan is implementable.
