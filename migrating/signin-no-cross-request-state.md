- **WARNING: kit 0.6.2 and 0.7.0 must not be used for sign-in; use 0.7.1 (fix).** Both keep Better Auth's object (and the promises it made by awaiting I/O) across requests in an isolate; Cloudflare forbids using a promise made by a request that has ended, so on Cloudflare about a quarter of real sign-ins failed (« Worker threw exception », sign-outs 500, signed-in calls 401, « This promise was created by a request that has since ended ») while node tests passed. Apps on 0.5.x sign-in are not affected; an app that deployed 0.6.2 or 0.7.0 sign-in rolls back or bumps to 0.7.1 now. `@hachej/boring-ui-kit/signin` 0.7.1 keeps nothing between requests: `signIn(...)` builds Better Auth at every request (CPU only, no query: the tables are your deploy migration) with no module state, no cache and no kept promise; `makeAuth` no longer caches and `resetSignInCaches()` stays as a no-op. A linked app asks Studio for its keys and owner list at each request that needs them, as 0.5.x did. THE MIGRATION STEP IS UNCHANGED and still required before the bump: copy `node_modules/@hachej/boring-ui-kit/dist/signin/migration.sql` into your next D1 migration and run `wrangler d1 migrations apply`, or sign-in answers 503 `SIGNIN_TABLES_MISSING`. Tests: `@hachej/boring-ui-kit/signin/testing` now ends each request's statements and queries with the request (`endsWithRequest`, `countingD1().epochs()`) and checks that every request's sign-in has a Better Auth of its own, so a sign-in that keeps anything of an earlier request fails `assertSignInQueryBudget`; this models Cloudflare's rule and cannot see inside Better Auth's own promises (the structural check stands in for them), so run many real sign-ins on a draft deploy (`wrangler tail --status error`) before going live. The kit's own `npm run test:signin-workerd` drives sign-ups, sign-ins, sessions and sign-outs, sequential and concurrent, through the kit on workerd itself.
