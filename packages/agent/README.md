# @hachej/boring-agent

/native re-exports exact Pi handles, configuration, task/view types and native ToolRegistration/ToolExecutionApi/ToolExecutionResult/hooks. Use upstream defineTool, registry installation and runtime values directly. There is no parallel Boring HostOperation/RuntimeSchema/tool engine.

/contracts contains only borrowed attachment and original runtime-question/delivery references. Passive attachment takes the native Harness, not a second possibly unrelated writable Registry. Host subtypes retain their native handle. Domain services keep their own signatures; no file package is required to configure an agent.

`attachHarness({ harness })` preserves the exact host handle. It acquires no observers or resources, so detaching is passive and never closes the host. Use native observation APIs directly and release their subscriptions under their own owner.

## One file tool set: the guard

The agent edits files with Pi's own `read`, `write`, `edit` and `bash` over the workspace's `ExecutionEnv`; Boring adds no replacement file-editing tools. The optional [document readers](#shared-document-readers) extract PDF and spreadsheet content without replacing native `read`. `createFileGuard({ workspace, resolveAccess?, name? })` from `@hachej/boring-agent/file-guard` returns a native extension (named `name`, default `boring.files.guard`: two agents with different workspaces in one registry need two names, or the last installed guard wraps both) that wraps those three tools with the public `wrapTool` (select it after the extension that registers them). Every wrapped call runs inside the workspace provider's mutation queue (`@hachej/boring-files/workspace`), so a viewer save cannot land between `edit`'s internal read and its write. `workspace` is the call's workspace resolved like Pi's environment, or one binding `{ files, root, access? }` (see [Workspace per call](#workspace-per-call)); `resolveAccess` defaults to the binding's `access`. A genuine `read` call records the file's revision as the conversation's last-read revision of that workspace and path (`baselineKey`) in a native conversation document (`lastReadRevisions`, kept across restarts; a fork starts empty); `edit`'s internal read records nothing. `write` and `edit` of a file that exists are refused unless the conversation has read it and its revision still equals the recorded one, and the refusal tells the model to read the file again. Creating a file is allowed only while it is absent. The guard fails closed: an unresolvable workspace, a refused provider read, a path outside the root, a link that leads outside it and a path that does not exist (so Pi's read never falls back to another spelling of it, such as an NFD name) (resolved through the env's `canonicalPath`, so also a new file under a link directory) are refused for `read` as well as `write` and `edit`; nothing falls through to Pi's native tool. After a successful `write` or `edit` the baseline is the revision just written, and the guard calls the provider's `record` (owner ruling 2: observed, never receipted): the file's history gains the written revision with source `agent` (and the bytes it replaced, read before the tool ran when that revision is not already retained), and the workspace's change feed an `agent` event with the conversation. Nothing enters the publication journal. Pi's `edit` tries an exact match first and falls back to a fuzzy one (Unicode normalisation, trailing whitespace, smart quotes, dashes and special spaces); the guard does not change that. A `bash` write is not intercepted, but it changes the revision, so the next `write` or `edit` of that file is refused until it is read; it reaches the change feed (no history) through the file system's watcher or the host's `poll()` at turn end. The guard adds no strictness option and no file API of its own.

## Workspace per call

`@hachej/boring-agent/workspaces` resolves the workspace of each call the way Pi resolves its environment, so one harness and one agent definition serve several people, each conversation in its own workspace. A `WorkspaceResolver` is `(target, context) => binding | undefined` with Pi's `EnvTarget`; a binding is `{ id?, files, root, env?, access? }` (`files` the workspace provider, `root` as the env names it, `env` the instance Pi uses, `access` the agent's principal). The guard, `present` and host tools (the studio's canvas tools) call `workspaceFor(resolver, api, context)`, which builds the target from the call (`callTarget`) and refuses a binding whose `env` is not the call's `api.env`. `constantWorkspace(binding)` is the single-workspace case; passing a binding where a resolver is expected wraps it. The first-class way needs no resolver at all: `withWorkspace(env, binding)` attaches a binding to an env (every `createWorkspaceCache` entry does it), and a tool given no `workspace` resolves `workspaceOfEnv(api.env)`, the workspace of the env the host's `HarnessOptions.env` returned for that call, so the host wires one function. A binding may also carry the workspace's git `repository` (`working_git` uses it).

`createWorkspaceCache({ key, open, atCwd?, idleMs?, busy?, onError? })` gives a host both sides from one entry per key: `env` for `HarnessOptions.env`, `workspace` for the tools, `acquire(key)` for viewer and HTTP routes after authentication (the lease's `release` never closes), `keys()` and `close()`. A workspace opens once per key, and closes after `idleMs` with no lease when `busy(key)` is not true. `rootConversation(session, id, context)` follows the owner edge of a task-owned conversation (a subagent's child) to the conversation whose workspace it uses. A `CredentialResolver` `(target, context, { tool, server? })` is the host's per-call secret lookup; tools call it at execute time and keep the value in memory only.

For a conversation with a different working directory, supply `atCwd(workspace, cwd, context)` to return an independent native environment over the same workspace. The cache retains that view per directory and attaches the original provider and access binding. The workspace owner closes any resources the callback acquires. Without this callback, a different directory is refused. Never mutate the shared environment's `cwd` or start a second remote workspace to create a directory view.

`createHarnessPool({ create, context, idleMs?, onError? })` from `@hachej/boring-agent/harness-pool` is the alternative: one harness per owner, opened by the host's `create(owner)` on first use (never shared, concurrent first uses open it once), held by `acquire`/`use`, by `respond` until a streaming response body ends, and closed once idle with no live task or submission. `owners()` and `opened()` read what is open without holding it. Choosing between them: [FILES-GIT-EXEC.md](../../docs/architecture/FILES-GIT-EXEC.md#workspace-per-call).

## Conversations

`@hachej/boring-agent/conversations` is a conversation list over native Pi. `createConversations({ harness, context, now?, titleLength?, previewLength?, onError? })` keeps one native conversation document per conversation (`conversationMetadata`, kind `boring.conversation.metadata`, `fork: 'initial'`): the host's `owner` key, a `title` (set by `create`/`rename`, otherwise derived once from the first user message), `createdAt`, `updatedAt` (last activity), a bounded `lastMessage` preview of the last user or assistant text (mention `<file>` blocks excluded), `archived` and `deletedAt`. The metadata of a turn is written after its entries commit: the module observes `harness.subscribeCommits` (no polling, no transcript scan) and one queued writer applies the latest message of each conversation. Only conversations it created (or `adopt`ed) are managed; any other conversation, including a native fork made elsewhere, is never listed.

`create(owner, { title?, start? })` writes the metadata in the creating commit (`start(init)` creates the native conversation with the host's agent, for example `definition.createConversation(harness, context, { init })`). `list({ owner, archived?, query?, limit?, cursor? })` returns the owner's summaries newest activity first; `query` is a case-insensitive substring of the title or the last message. `rename`, `archive(owner, id, archived)`, `get`, `open` and `fork(owner, id, at)` (native `Conversation.fork`, the history up to and including entry `at`, titled "<title> (fork)") refuse another owner's or a deleted conversation by returning `undefined`. `delete` aborts the conversation's ordinary work and sets `deletedAt`: Pi has no conversation deletion, so the records stay in the session storage and their retention is the host's (prune or drop the storage). `adopt(id, owner)` manages an existing conversation once (title and preview from a bounded history read), for migrating a host's own index. Owner scoping and authorization stay with the host: `createConversationsHandler({ conversations, authenticate })` is a Fetch handler (`GET` lists with `?archived=1|all&q=&limit=&cursor=`; `POST ?op=create|rename|archive|delete|fork` with a JSON body) whose `authenticate(request)` returns `{ owner, start?, opened?, deleted?, allow? }` or null.

`conversationTitle(conversation, context, cache?)` is the title of a conversation that has none stored: its first user message, clipped to 80 characters. The first message never changes, so a non-null title is cached (`cache`: a `Map` keyed by the conversation id) and the history is read once; `null` (no user message yet) is not cached. A host's list poll passes its cache rather than paging the history again.

Listing reads every conversation record (`scanConversations`) and one metadata document each: Pi's storage has no query over document values or text index, so search is an in-memory substring match. A host with many conversations keeps its own index.

## Mentions

`createMentionResolver({ read, mode?, limits? })` from `@hachej/boring-agent/mentions` turns the `@path` mentions of a submitted message into parts the host adds before submission. The default `mode: 'inline'` puts the text of each file (and images) in the message; documents (PDF, office, zip, epub) are never decoded as text. With `mode: 'reference'` each mention is one `<file path type size />` part and no content, so uploads do not fill the context: the agent reads the file with its tools (Pi `read`, which `createConvertingRead` from `@hachej/boring-agent/file-convert` extends to PDF, office and images) when it needs to.

## Model gateway

`@hachej/boring-agent/model-gateway` (server only: it holds the provider key) is `createModelGateway({ upstream, allow, budget, authorize, log?, basePath? })`, a Fetch handler for `POST <basePath>/v1/chat/completions` (OpenAI-compatible, JSON or SSE passed through) and `GET <basePath>/v1/models`. `authorize(request)` returns the person's id from the app session (else 401); `allow` lists gateway model ids or maps them to upstream ids (else 403); `budget.admit` refuses (429, `Retry-After`) or admits with the output ceiling to send (`memoryBudget({ requestsPerMinute, maxTokensPerRequest })` is the in-process reference). The forwarded body is rebuilt from an allowlist of fields and no request header is forwarded; the upstream (`openAICompatibleUpstream`, `anthropicUpstream`, keyless `scriptedUpstream`) adds the key. Upstream failures are 502 with the gateway's own message, never the upstream body. `log` receives person, model, status, code, latency and token counts only. It imports no node or Pi module, so the same code can run as a shared service.

`@hachej/boring-agent/gateway-provider` is the browser half: `gatewayProvider({ baseUrl, models, getAuth })` returns a native Pi provider (Pi's `openai-completions` API at `<baseUrl>/v1`) whose only credential is `getAuth()`'s session headers, read on every request. Use it with `createModels().setProvider(...)` and any native model call.

## Metering

`@hachej/boring-agent/metering` ports the v2 credits contract onto native Pi. The host owns the ledger, the price and the policy (INVARIANTS: budgets are host data); the module decides only when to call the ledger. Pi has no hook that can hold or refuse a model request (`beforeRequest` only replaces messages, `afterResponse` observes), so the fence is submission admission, and usage is read from the durable transcript, not from a second usage store (SPEC "Model admission, usage and settings").

- Scope (host-owned): `MeteringScope` is `{ userId, workspaceId?, attributes? }`, the host's mapping of its own authentication (attributes: at most 16 flat JSON-safe values such as a plan or tenant, passed through untouched). Every sink call carries the run scope: that plus `conversationId`, `requestId` and `runId`.
- `MeteringSink` (v2's `AgentMeteringSink`): `isEnabled?`, `reserveRun(input)` → `{ reservationId }` or `{ kind: 'refused', reason }` (a throw also refuses: fail closed), `recordUsage(input)` → `{ billedMicros }`, `settleRun`, `releaseRun`, and `openRuns()` for recovery. All idempotent on `runId` and `usageId`. The reservation also carries `model: { provider, id }`, the model the run will use (the conversation's selected model resolved through Pi's `Conversation.agent` at submit time, so a host can admit per model as v2 governance did), `kind` (`input`, or the input's native `whenBusy` choice `followUp` / `steer`), a `message` preview (text, whitespace collapsed, at most `MESSAGE_PREVIEW_LENGTH` = 280 characters) and the raw `content`. Usage keeps its own per-entry `model` (a run can switch models).
- `createMeter({ sink, context, price?, models?, markup?, onError? })`. `meter.conversation(conversation, scope)` is the native conversation with an input `submit` that reserves first; a refusal throws `MeteringRefused` and nothing is submitted (the chat transport answers it with 402 `submission-refused` and the ledger's message; `@hachej/boring-ui-kit/remote-chat` turns that into a blocked send showing the message). The run id is `run:<conversation>:<requestId>`, so a client retry reserves nothing new.
- Recording: on every conversation change the meter reads each open run's submission record and the entries from its user entry to the next placed input; every assistant entry (and tool result) carrying `usage` is recorded once under `entry:<conversation>:<entry>` (the native attempt identity), priced `price(usage, model) * markup` (default `catalogPrice(models)`: Pi's `calculateCost` with the model's rates, else the provider-reported cost, in micro-dollars).
- Termination, when the submission is `done` or `unanswered`, exactly one call: a usage write still failing charges the hold (`usage-write-failed`); a person's stop settles what was billed or frees the hold (`cancelled`); an aborted attempt with no billed usage (interrupted, usage unknown) or a non-zero report priced to nothing charges the hold (`fallback-charge`); billed usage settles; complete all-zero reports settle at zero; an answer without any usage report charges the hold; no model call at all frees it (`no-model-call`, `error-before-usage`, `not-started`).
- `meter.recover(harness)` after a restart: each run the ledger still holds open is finished from Pi's durable state (finished: settle with the replayed usage; interrupted with unknown usage: charge the hold once Pi's recovery ends the run; never submitted: release), and the rest are watched.
- Ledgers: `createMemoryLedger(options)` and `createSqliteLedger({ connection, ...options })` (a borrowed `SqliteConnection`) or `createSqliteLedger({ filename, sqlite?, ...options })` (a file the ledger opens with `openNodeConnection(filename, sqlite)` and closes on `close()`; `sqlite` is `SqliteSettings` from `@hachej/boring-files/sqlite`, local disk WAL by default; several processes on one file on a network file system use `{ journalMode: 'delete', lockingMode: 'normal' }`, one owner `sqliteSettings.networkFilesystem`). Every ledger write is one write transaction (`BEGIN IMMEDIATE`), so concurrent writers wait up to the busy timeout instead of failing, and a reservation's balance check and hold commit together (no double spend; four-process test in `test/packages/agent.test.mjs`). Tables `boring_metering_*` with each run's scope, model and kind, charges keyed by (run, step) with the usage's model; tables of the earlier account-keyed shape are refused, not migrated). Options: `holdMicros`, a number or a function of the reservation (model-aware admission: a costly model holds more, so a low balance refuses it while the default model is still admitted); `balanceKey?(scope)`, the balance a run draws on (default its `userId`; `scope => scope.workspaceId ?? scope.userId` pools a workspace); `refusal?(available, hold, input)`. Both add `balance(key)` and an idempotent `grant(key, amountMicros, grantId)`; a reservation is refused when the available balance (grants minus charges minus unspent open holds) is below its hold; a fallback charge tops the run's charges up to its hold.

Limits: a run is admitted against its hold, not stopped mid-run (no per-call fence in Pi), so one run can overdraw into recoverable debt that refuses the next one; usage of child conversations (subagents) and of input submitted without the metered view (channels) is not metered; a sink call that keeps failing is retried on the next change of that conversation or by `recover`. The browser-agent model gateway keeps its own per-request `ModelBudget.admit`; a host bills browser runs by calling its ledger from that `admit`.

## Artifacts

`createPresentTool({ workspace, resolveAccess?, maxBytes? })` from `@hachej/boring-agent/artifacts` returns the native `present(path)` tool (its workspace resolved per call like the guard's): the agent writes a workspace file with its ordinary file tools and presents it, and the chat shows a card that points at that file (`target`, the revision shown, no `id` or `ordinal`). The file's versions are the history of the workspace provider (`@hachej/boring-files/workspace`, whose `keep` retains the presented revision); a card of an older revision pins it and a card of the newest follows the file as it changes. The tool writes nothing and refuses files that are missing, not UTF-8 text or larger than 256 KiB. An opt-in `ack: { timeoutMs?, viewers? }` makes `present` wait until a page has mounted the presented revision: the page answers `{ kind: 'opened', instanceId, path, revision }` or `{ kind: 'refused', reason }` through the chat's `answer` (the transport's `?op=answer`), and the result carries `opened: true` with `viewer`, `opened: false` with `refused` (for example `closed by user`), `opened: 'unconfirmed'` after `timeoutMs` (default 15 s) or `opened: false, viewer: 'none'` at once when `viewers()` says no page watches the conversation. The wait is the durable wait of `ask_user` (`packages/agent/src/view-open.ts`, a conversation document keyed by the call); the deadline is stored, so a restart cannot extend it, and the first valid answer wins. Without `ack` the result is unchanged. `answerViewOpen` settles an answer; the host chains it with `answerUserQuestion` and `answerBrowserTask` in its `answer` handler. How to use it is in the tool's own description, so a host does not repeat it in its prompt: substantial output goes to a file that is then presented, short answers (and anything asked for in the chat) stay in the chat, and a revision re-reads the file, changes it at the same path and presents it again. A host adds only what is its own, such as what its HTML preview allows.

### A view that is not a document (a dashboard)

A view the agent opens, such as a dashboard, is presented the same way: it is a small workspace file that names what to show (for example `sales.dashboard.json`), and the app registers an artifact kind that draws it. There is no second channel: the same `ack` answers for it. Mark the kind `waitsForReady: true` when its renderer loads asynchronously: the panel then reports the mount (and the page confirms the `present` call) only after the renderer calls `onReady` for the revision shown. `onFailed(reason)`, or a renderer that throws, refuses the call with that reason, and a renderer that never becomes ready leaves it `unconfirmed` at the deadline. A kind without `waitsForReady` is confirmed as soon as its file is read.

```tsx
// Server: the agent writes sales.dashboard.json, then calls present('sales.dashboard.json').
createPresentTool({ workspace, ack: { timeoutMs: 15_000 } });
// -> { kind: 'presented', artifact, opened: true, viewer } | { opened: false, refused: 'the sales query failed' } | { opened: 'unconfirmed', timeoutMs }

// Page (pi-app block): the kind confirms the view only once its data has loaded.
const dashboard: ArtifactKind = {
  match: target => target.resource.path.endsWith('.dashboard.json'),
  label: 'Dashboard',
  waitsForReady: true,
  renderer: ({ text, onReady, onFailed }) => <SalesDashboard spec={JSON.parse(text)} onLoaded={onReady} onError={error => onFailed?.(error.message)} />,
};
<AgentWorkspace {...workspace} artifactKinds={[dashboard, ...defaultKinds()]} />; // defaultKinds: the pi-app-kinds item
```

`workspaceMentionReader(files, access, { maxReadBytes? })` is the reader for a host with a workspace provider: it reads the person's own published view through the provider (the access check the file viewers use) and has no containment check of its own. A host that has no provider has no reader here; it writes a `MentionReader` over whatever it does have.

The descriptor's `id` and `ordinal` are optional and `present` sets neither; `parseArtifact` validates a descriptor and has no Pi runtime dependency (the copied `pi-chat` registry item carries the same validator for the browser).

## Agent state refresh and converted file text

`refreshAgentState({ conversations, agent, read, write, context })` from `@hachej/boring-agent/agents` brings existing conversations up to a changed deployment. A conversation keeps the agent it was created with, so when the agent's `instructions` or default `thinkingLevel` change, the helper calls `configure` on each conversation. The host stores a hash of `[instructions, thinkingLevel]` (`read()` returns the stored hash, `write(hash)` stores the new one); it configures nothing when the hash is unchanged and writes the new hash last, so a failed run is retried. It returns how many conversations were configured.

### Add an extension to an existing conversation

`addExtension(conversation, extension, context)` from `@hachej/boring-agent/agents` adds one Pi extension (for example `createApprovalExtension(...)` or one that registers a tool) to a conversation that already exists; its next turn runs with it. It edits the conversation's stored `pi.agent` selection in one native `Conversation.commit` (Pi's public `AgentDoc`): the name is appended to the conversation's own list, so it keeps its other extensions and picks up no other agent's, and the extension's tools are enabled and offered even when the conversation lists its tools. Adding it twice changes nothing; remove it with native `conversation.configure({ extensions: { remove: [extension] } }, context)`. Native `configure({ extensions: { add } })` is not the same: on a `defineAgent` conversation it replaces the stored list with an edit of the host default selection.

```ts
const registry = createRegistry();
agent.install(registry);
registry.install(approval); // at every Harness open: the conversation stores the name only
const conversation = await harness.conversation(id, context);
await addExtension(conversation, approval, context);
```

The selection is durable (it is in the conversation's Pi state and survives a reopen), but an extension is host code and is not stored: install it in the registry every time the Harness opens, or its name selects nothing. Installing it does not add it to other `defineAgent` conversations, whose lists are explicit; a conversation with no stored list (such as `harness.root()` without `agent`) follows the host default selection, which is every installed extension unless `HarnessSettings.extensions` names them.

`createConvertingRead({ workspace?, resolveAccess?, convert?, cache?, maxBytes?, name? })` from `@hachej/boring-agent/file-convert` returns an extension that wraps Pi's native `read` (`wrapTool`); there is one `read`, and no second tool. Text goes to Pi's read untouched. A PDF, an office document or an image goes to the host's `convert({ name, mediaType, bytes })`, once per saved revision (cached by path and revision), and the converted text is paged the way Pi pages a text file: `offset` is the 1-based line to start at, `limit` a number of lines, a page ends at 2000 lines or 50 KB, and the note names the `offset` to continue from. What is text and what is not comes from one table, `fileKind` in `@hachej/boring-agent/file-types`, which looks at the extension and the leading bytes (Pi's read returns garbled text for a PDF, so a PDF is recognised by `%PDF-` even under another name); the mention resolver uses the same table. An archive or other binary file answers `unsupported` and is never converted; without `convert`, an image uses Pi's native behaviour and a PDF or office file answers `unsupported`. A line of converted text above 50 KB is split into 50 KB segments, each counted as one line, with a warning, so nothing is cut. The type is sniffed on the bytes the provider returns after its access check, and the converter is told the media type the file's signature names (a PDF named `.txt` arrives as `application/pdf`). The file is read through the workspace provider, so its access policy applies; a path the wrapper cannot place inside the workspace is left to the native read. Install it before `createFileGuard`, so the guard stays outermost and refuses anything outside the workspace first. `workersAiMarkdown(env.AI)` adapts a Workers AI `toMarkdown` binding to `convert` without a Cloudflare types dependency.

## Shared document readers

`@hachej/boring-agent/documents` exports `documentTools({ readBytes, ocr?, images? })`, `sniff(bytes, name?)` and `readStored(path, bytes, { images })`. These are native `defineTool` registrations and a native read-result helper, not a filesystem or another `read` tool. Pi's own `read` is unchanged; `file-convert` above remains the host-conversion alternative.

```ts
import { defineExtension } from '@earendil-works/pi-durable';
import { documentTools, readStored } from '@hachej/boring-agent/documents';

// readBytes is the host's authorized read through its one workspace provider.
const tools = documentTools({ readBytes, ocr });
registry.install(defineExtension({ name: 'app.documents', tools }));
// A host's stored-file read path can return this native ToolExecutionResult:
const result = readStored(path, await readBytes(path), { images: true });
```

The host supplies byte access and optional OCR; this package performs no file/network I/O and holds no credentials. Bind `readBytes(path)` to the authorized workspace/view for this conversation. Read failures propagate as native tool errors. Both readers use `replay: 'safe'`; recovery may reread bytes or call OCR again, so the host owns stable revisions, current authorization and OCR cost policy.

- `read_pdf(path, pages?)` returns `{ path, totalPages, pages: [{ n, text, ocr?, truncated? }], untrusted: true }`. Page lists such as `"1-3,5"` are sorted and deduplicated, at most 30 pages per call; without a list, the first 30 pages and a `next` hint when more remain. Each page is capped at 20,000 characters. Requested pages without text go to `ocr(bytes, pageNumbers)`, which returns `{ pages?: [{ n, text? }], provider? }`. Only matching scanned pages are replaced and marked `ocr: true`; absent or failed OCR adds a note. Unlike the Factory reference's media-type argument, this callback receives the selected scanned page numbers.
- `read_spreadsheet(path, sheet?, range?)` reads xlsx, xls, ods and CSV. It returns `sheetNames` and `{ name, rows, columns, shown, csv, truncated? }` for each selected sheet, plus `untrusted: true`. The limits are 20 sheets, 200 rows per sheet by default, 1,000 with a cell range such as `A1:C1500`, and 60,000 CSV characters per sheet. Formulas use their last computed values, never execute.
- `sniff` uses magic numbers and ZIP entry names, not extensions (except CSV versus other UTF-8 text). `readStored` returns JSON text containing `{ path, content }` for text/CSV; images up to 4 MiB add native `ImageContent` when `images` is true. Other binaries, oversized images and image-incapable models return `{ path, type, size, error }`; PDF/spreadsheet refusals point to their reader. `images` affects this helper, not the two extraction tools.

Results use native `output` for the model and the same metadata in `details`. As in the reference, typed refusals are ordinary results carrying `error`, not `isError: true`. Document content is untrusted evidence, never instructions or consent. The readers set Pi's native output byte limit to 8 MiB to retain valid JSON at the extraction caps; the JSON occupies one native output line. These are returned-extraction limits, not bounds on input bytes or parser memory/CPU. Enforce input and resource budgets in the host.

PDF reading uses the pinned regular dependency `unpdf@1.9.1` (MIT). Spreadsheet reading needs the optional peer `xlsx` (SheetJS, Apache-2.0); install the official distribution in the host with `npm i https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`, not npm's old `xlsx@0.18.5`. Without it, the spreadsheet tool returns a clear refusal; PDF reading still works. Both packages are imported lazily inside their reader only. Their notices ship in `THIRD_PARTY_NOTICES.md`. `test/packages/agent-documents.test.mjs` drives public registrations through a real Harness with generated fictional files, and `npm run test:question-consumer` exercises the packed agent without SheetJS; no live OCR provider is qualified.

## Approval gate

`requireApproval(tool, { summarize })` from `@hachej/boring-agent/approval` wraps a native tool so each call waits for the person's Approve or Deny before `execute`. It reuses the ask-user mechanism (`askPerson` from `@hachej/boring-agent/ask-user`): a conversation document keyed by the tool call ID, answered with `answerUserQuestion` through the chat transport's `answer` operation, and shown by the `pi-chat` approval card. The check runs inside the tool's own execution in host code, so the model cannot skip it. While the call waits, the one-line `summarize` text is also published as the call's running details under `APPROVAL_DETAILS` (it stays as the result's details unless the tool returns its own). That is also how `pi-chat` recognizes a gated call: no list of tool names is needed. The card shows the summary as the headline with the raw arguments collapsed. Deny (or a stopped conversation) returns an error result starting `DENIED_PREFIX` and `execute` never runs. The wrapper is replay-safe: a pending approval survives a restart, and a retained native memo makes execution at most once (after a crash during execution the model gets an "outcome unknown" error instead of a repeat of the change). Reads are simply not wrapped.

`createSandboxExtension({ tools, flags?, simulate? })` from `@hachej/boring-agent/sandbox` is a fail-closed sandbox as a native extension (`boring.sandbox`, or `name`). Its wraps replace each listed tool that the host flags `mutates` or `writes`, or does not declare `sandboxSafe` or `mutates: false`/`writes: false` (in `flags`), with a recorder: the call is never executed, the model gets `simulate(name, args)` (default `defaultAck`), and the result's details carry `{ simulated: true, tool, arguments }` under `SANDBOX_DETAILS`, which `simulatedCalls(results)` reads back. Its `beforeTool` hook blocks any call whose name is not in `tools`, so a tool added mid-run cannot run unnamed. Select it per conversation by including it in the complete selected list and applying that list with `configure({ extensions: selected })` (not `add`: defaults keep their positions, so an `add` list does not show the effective order), after any approval extension, so no question is asked inside a sandbox. **Composition limit (host-owned ordering):** the sandbox must be the last wrap of each recorded tool. A wrap selected after it (for example `createConvertingRead` on `read`) replaces the recorder's `execute`, and that call runs for real. Pi 1.2 has no public seam that tells the executing phase which composed tool it runs, so the sandbox cannot refuse this at call time. The host checks the order at setup with `assertSandboxLast(selected, sandbox)` over the COMPLETE selected list, the same array it applies with `configure({ extensions: selected })` (`@hachej/boring-agent/sandbox`); it throws on a later wrap of a recorded tool. Nothing in Pi calls it, so a host that composes extensions without it has no protection against that ordering. The gap is recorded in [docs/upstream/pi-hookapi-composed-tool.md](../../docs/upstream/pi-hookapi-composed-tool.md). The name gate in `beforeTool` is public and holds at call time: a call to a tool the sandbox does not name is refused.

`createApprovalExtension({ name?, tools: { bash: true, write_note: { summarize, when } } })` is the same gate as an opt-in native extension: it brings no tools, only native `wraps` that decorate whichever tool of each name wins in a conversation, including Pi's stock `bash`, `write` and `edit`. Pi applies wraps only where the extension is selected, so the gate is per conversation: `conversation.configure({ extensions: { add: [approvals] } })` turns it on and `remove` turns it off from the next call. `when(args, call)` lets a rule ask only for some calls (for example any method but GET); `summarize(args, call)` writes the card's headline (default: the tool name and its arguments). `call` is `{ conversationId, callId, toolName }`, so a host with one conversation per site or project can name it in the headline. Approval extensions compose: a tool already gated is not gated again, so the first selected rule for a tool decides. `requireApproval(tool, { summarize, when? })` remains the building block for a tool you define yourself.

Code mode: gated tools are native tools and must not be exposed to a code-mode sandbox, whose nested calls cannot reach a person. Give `run_code` the read tools only and send changes through the gated native tool. `isApprovalGated(tool)` lets a host filter automatically.

## OptChat memory

`@hachej/boring-agent/memory/optchat` is Victor Taelin's [OptChat](https://gist.github.com/VictorTaelin/91837951a5ce5b38f341ec1ba1df6449), aligned with [uniichat at 0500bf6](https://github.com/VictorTaelin/uniichat/tree/0500bf6a8ea4bf0ce047488562022b1b6532cc30) as one native pi-durable extension: an endless conversation whose memory is the conversation itself, shown to the model as a compressed tree. Credit for the idea, the algorithm and the summarizer prompt is his; this package maps it onto Pi.

```ts
const memory = createOptChatMemory({ harness: () => harness, context, summarizer: { models, model: { provider, modelId } } });
registry.install(memory.extension);                                              // like any extension
await conversation.configure({ extensions: { add: [memory.extension] } }, context);    // on, for this conversation
await conversation.configure({ extensions: { remove: [memory.extension] } }, context); // off again
```

Pi applies an extension's hooks only in conversations that select it, so memory is opt-in per conversation and there is no separate mode. A host that selects extensions by default selects it everywhere; give conversations an explicit `extensions` list to keep it opt-in. `createOptChatMemory(options)` returns `{ extension, nap(id), stats(id), zoom(id, leafId, n), date(id, leafId), forgetMessage(id, messageIndex), forget(id), dispose() }`. Options: `harness`, `context` (long-lived, for background work), `summarizer` (required: `{ model }`, where `model` may be a function `(conversationId) => ModelRef`, sync or async, for example that conversation's own model, and `models` defaults to the Harness's; or `{ summarize(job, signal) }` returning one line), `nodeBytes` (512), `viewBytes` (128000), `compactBytes` (32000, the cold-start/callback compactor view), `foldHighWater` (1.25) and `foldLowWater` (0.75), fractions of both view budgets, `notes` (seed strings, stored once per conversation before the transcript), `workOf(message)` (host classification of subagent or job reports), `jobs` (64, how many summary tasks of a conversation the host keeps live at once), `tries` (5), `cap` (30000), `retryMs` (10000 initially, doubling after each failure to at most 60000), `settleTimeoutMs` (60000), `agentName`, `name`, `onError`. `dispose()` only stops this process's waits: the summary tasks belong to Pi, which keeps and recovers them, so it is harmless to skip and safe to call before `harness.close`.

| Reference | Here |
| --- | --- |
| Append-only log of user, talk, tool and echo messages | The Pi transcript, never rewritten. Leaves are derived from the model context: a user message is `user`, assistant text `talk`, each tool call `tool`, each tool result `echo`; thinking is not logged. A leaf over `cap` characters keeps head and tail. Seeded `note` leaves precede them; messages marked by `workOf` become one `work` leaf |
| Summary tree: node (l, i) covers messages [i·2^l, (i+1)·2^l), at most `nodeBytes` | The same, purely binary. A short message, or two children that fit together, are their own text and cost no call |
| The view tiles the whole chat, one `id+n\|text` line per node, fit incrementally by merging the most due pair (age / 2^(level+2)), never splitting | The checkpoint fold (`advanceFold`): append between checkpoints; above 125% of the budget, merge deterministically down to 75%. Both fractions are configurable. The public four-argument core helper retains strict fitting. `renderView` produces the `<chat>` block |
| Each turn calls the model with [system][view][new message] | `GenerationTask.beforeRequest` replaces the messages before the current turn with the view, as four-line text blocks at the start of the current turn's first message. The turn in progress starts at the latest user or work message. Work reports and sibling results whose tool calls fell outside the turn become ordinary user-role input, with their full text preserved. Every positional system message is kept in order. The explanation of the view is a prompt section, so the system prompt and tools never change between calls |
| Compactor: context first, no ids, scale line, resubmit with the cut at the limit, `JOBS` in parallel, patient retry | The same protocol (`askModel`), run by native pi-durable tasks: each node `(level, index, fingerprint)` is one `boring.memory.optchat.node` task (shipped in the extension's `tasks`, input `{ key, level, index, of, upTo }`, one `summarize` phase) that calls the summarizer through `runtime.models` (or your `summarize`) and, in one commit, writes the node and the summarizer's usage into the extension's state. Pi schedules, runs and recovers them. See below |
| A turn waits until every line of the view is a summary and never shows cut text | The request waits up to `settleTimeoutMs`; after that the missing lines show `(not summarized yet: zoom it)`, never a clipped message, and `zoom(id, 1)` returns the message whole |
| `zoom(id, n)` and `date(id)` | Native replay-safe tools of the same names |
| Summary files | A conversation document family (`boring.memory.optchat.nodes`, shards of 64 nodes per level, `fork: 'current'`), one fingerprint per node over the content it covers. A fork or an edit never shows a summary of different content: a stale node is unbuilt until rebuilt |

What is native, what is host-side:

- **Tasks.** The host creates node tasks with `conversation.commit(tx => tx.createTask(...))` (hooks are read-only) as `background: true`, conversation-owned tasks: they never keep the conversation busy, never block or get aborted with the user's run (`conversation.abort()` leaves them; `abort(context, { background: true })` aborts them), and show in `harness.taskGraph()` and `harness.inspect()`. A pending task after a restart is resumed by Pi once the extension is installed again (the extension carries the task definition; the options must be the same).
- **Triggers (host admission, not scheduling).** After an answer (`onYield`, once the run is idle) and when a request needs its view (`beforeRequest`). A trigger creates the tasks of the nodes whose sources exist and whose preceding view is summarized. One live task per node key, found by scanning native tasks in the same commit that creates them. `jobs` caps how many are live per conversation; Pi has no task concurrency setting, so this is the host's admission cap and Pi's scheduler decides when they run. A node's parent is created by the next trigger or by the waiting `nap` or request, once its children are built.
- **Waiting.** A request waits with `waitForTask` on the live node tasks, up to `settleTimeoutMs`, then shows the placeholder. `nap` waits until all nodes are built, including retries. These waits are in-process; if the process dies the tasks are not lost, only the cascade to parents waits for the next trigger.
- **Retry.** A failed node is a failed native task (`outcome.failed`). Its failure time and streak length live in `boring.memory.optchat.state` with call count and spend. The host's idle admission loop waits from `retryMs`, doubling to at most 60 seconds, then creates another native task without a new turn. `dispose()` aborts those waits, not Pi's tasks. After a process restart, `nap` or another trigger restarts admission. Requests retain their bounded wait and can show placeholders during an outage. `onError` reports only the first failure of a streak.
- **Usage.** In the commit that stores a node (or records its failure) the task adds the summarizer's usage, all attempts of the cut-and-resubmit loop included, to the extension's own state document (`boring.memory.optchat.state`), reported by `stats().compactor.usage`. It is not written into Pi's `pi.usage`: Pi has no public way for a task to record model usage (`recordUsage` is internal), so per BORING-PI-4 that guarantee is unavailable here rather than worked around; a public usage-recording seam is an upstream request. Hosts that budget model spend add `stats().compactor.usage` to `harness.usage()`. Task and document kinds are all in `boring.memory.optchat.*`; this package writes no `pi.*` document.
- **Still host-side.** The trigger and admission logic, the log cache and the summarizer prompt. Context refreshes reuse a prior leaf only after exact kind, capped-text and timestamp comparison, avoiding repeated byte counting and hashing without trusting native message identity. The emitted turn and compactor tilings, open flags and content fingerprints are retained in `boring.memory.optchat.fold` (no duplicated message or summary text), so cache eviction and restart restore the same prefix with unchanged options and history. A sent interior placeholder stays frozen until a checkpoint (the tail may settle); later summaries remain accessible through zoom. History changes, forgetting or changed fold options rebuild the view. A custom `summarize` function has no model usage to record. A model call interrupted by a crash is rerun from the start of the task, and its spend is not recorded.

Deviations, honestly:

- The log is Pi's model context, not an OptChat file, so ids are positions in that context. A native compaction, reset or edit that changes earlier messages invalidates the summaries it touches (fingerprints), and the view is refolded. `beforeCompact` declines while the extension is selected: the view replaces compaction, and a native summary would cut the transcript the view is built from. That is the only effect on Pi's lifecycle.
- The current turn is verbatim (including its tool steps) instead of being summarized to one line each as soon as it is logged; it enters the view when the next user message arrives. A user message sent mid-run starts a new "current turn" for the next step.
- A request is rewritten once per attempt from the full context. The summaries are a cache rebuilt from the log; the summarizer's calls are not Pi generations: they run as Pi tasks and their usage is in `stats().compactor.usage`, not `pi.usage` (see above).
- Both views use four-line text blocks. Model compactor requests carry the entire last emitted turn view (bare lines), even when their job revisits older history; the admitted `upTo` still bounds the source they may summarize. Before the first turn, native documents retain one frozen, whole-block prefix within `compactBytes × foldHighWater`. Callback summarizers keep their past-only `compactBytes` context. The constant size example is in the summarizer system prompt rather than every job suffix. The first native task on a new conversation/model/prefix sends alone; other admitted tasks await its response, then send in parallel within the same `jobs` cap. Failure or cancellation releases the warmup wait. This is process-local request coordination, not a scheduler or proof a provider retained its cache.
- `stats().compactor.requests` exposes provider-reported input, cache reads/writes, output and cost for the most recent 256 responses booked by settled native tasks, including retries, oldest first. The history limit is `COMPACTOR_REQUEST_HISTORY_LIMIT`, next to `DEFAULTS`; lifetime `calls` and aggregate `usage` totals are not truncated. These records survive restart; old state documents start with no request records. Interrupted tasks can lose uncommitted usage, as before. Pi 1.2 exposes no per-block cache marker: the fictional Anthropic replay supplies host breakpoints and measures cold starts plus 100 turns at 600/full-fold and 400/default messages. It enforces ≥95% cache reads, fewer uncached tokens and no extra summarizer calls; this is not live-provider qualification. Longer cached context increases total input. Qualify the host's chosen budgets, breakpoints and retention with its provider. There is no separate `fsync` log or single-writer lock; Pi's storage owns durability. Summaries are read from documents on every request and stats call.
- Cost: the compactor makes about two calls per message, each carrying its small view as context. Choose a cheap summarizer model; the browser-agent example uses the chat model only because it has one.
- The package runs in Node and in a browser (no Node-only imports). Fictional-data tests are in `test/packages/agent.test.mjs`; `examples/bot` and `examples/browser-agent` have journeys.

### Forget a message

`await memory.forgetMessage(conversationId, messageIndex)` forgets one message in Pi's current model context. `messageIndex` is its zero-based position in `(await conversation.context(context)).messages`, including system-message positions. System messages cannot be forgotten. This is distinct from the leaf id used by `zoom`; seeded notes and assistant tool calls can shift leaf ids.

The operation replaces every leaf of that message with `(forgotten)` at the same positions. One native commit stores the tombstone and deletes those leaf summaries, their ancestors, later summaries and corresponding failure records. Once a model summarizer has used the shared prefix, forgetting conservatively deletes all summaries: earlier nodes and transitive parents can also copy later facts. That fact is retained across restart and summarizer configuration changes. With only callback summaries, later summaries can contain facts resolved from earlier context, so deleting only the logarithmic structural ancestors would leave copies behind. Rebuilding can therefore cost more than logarithmic work. Later leaves keep their ids and fingerprints. Native tasks rebuild the invalidated summaries. In-flight calls recheck the memory revision inside their commit and cannot restore old output. A chat request waiting on summaries also rechecks that revision before returning its rewritten messages. `nap` waits for rebuilding. Repeated forgetting is harmless. `forget(id)` only evicts the process cache and does not undo tombstones.

This changes active memory only, not requests already dispatched. Pi's session entries, native task history, underlying storage pages, provider logs, backups and copies quoted in other messages or existing forks are not erased. Indices address the current context, so a reset or history replacement requires the host to resolve positions again. Hosts must authorize the operation. Seed notes are stored once in `boring.memory.optchat.notes`; changing `options.notes` does not overwrite an existing conversation's notes.

Prompt wording and algorithm adaptations retain the upstream Apache-2.0 attribution in [NOTICE](NOTICE) and [the license copy](licenses/Apache-2.0.txt). The file headers identify the changes.

## Per-request prompt context

`@hachej/boring-agent/prompt-context` (`createPromptContext({ context })`) is one ordinary native extension whose `GenerationHooks.beforeRequest` (registered with `hook(GenerationTask, ...)`) runs before every request attempt, retries and crash recovery included. The hook's text is used for that request only: it is recomputed each time and never appended to the transcript. The text is one user-role `<request-context>...</request-context>` message placed immediately before the round's question when the final message is the user's question, otherwise at the tail (after tool results or an assistant continuation); system messages and earlier messages are unchanged, so the stable prefix stays cacheable.

Choose the seam by how the text changes and who should see it:

- Stable per-agent text (instructions, a fixed section): `AgentSpec.instructions` or a `PromptSection`. Pi stores a system entry whenever a section's text changes, so use it only for text that changes rarely.
- Volatile or private text (the open document, the time, a permission snapshot): this hook. Nothing is stored and the person does not see it in the history.
- Text the person should see and keep: `prepareInput` on the submit route, which becomes the user message.

`context({ conversationId, messages, signal })` returns the text (`undefined` or `''` adds nothing). The host keeps request-scoped state in its own store keyed by `conversationId` and reads it there; Pi's hook context carries no caller values. Install several extensions to compose independent contexts (they apply in install order).

Failure is fail-open and Pi's: a throwing `context` is reported through `HarnessOptions.onReport` and the request goes out without the context (Pi's `hooks.each`, scheduler.js). An aborted turn rethrows. This is advisory text, not policy or authorization; do not use it to enforce a decision. The text is sent to the model provider and gateways or telemetry that log request bodies may see it; the model can quote it into a stored assistant message. Compaction summarizes the stored transcript only, so the context is not folded into summaries. After a crash the hook runs again at recovery, so the value is fresh per attempt, not replayed. Placement: before the round's question when that is the last message; after tool results or an assistant continuation, at the tail. Tests: `test/packages/agent-prompt-context.test.mjs`.

Screen context: a browser can send what the person is looking at with each submit. `createRemoteChat({ requestContext })` adds the returned plain object to the submit body as `context`. In `ChatTransportAccess`, `requestContext(value)` receives it after validation and before `conversation.submit`; a value that is not a plain JSON object of at most 4 KB is `400 invalid-request`, and a host without `requestContext` ignores the field. The host stores `context` by conversation id in `requestContext` and renders it in `createPromptContext({ context })`; the transport keeps nothing. With `useRemoteChat` the context is the `requestContext` value as it is (`name`, `params`: a host written before placement keeps working) plus `placement` (`docked` or `floating`), reported by `PiChat` / `AmbientChat`; `PiChat` takes a `placement` prop for a host that floats it, as the `AgentLayer` does. `renderRequestContext(value)` (from `@hachej/boring-agent/prompt-context`) turns it into the agent's role and the screen for `createPromptContext`; placement changes behaviour, never authority (see [PAGE-TOOLS.md](../../docs/architecture/PAGE-TOOLS.md)). Tests: `test/packages/agent-chat-transport-context.test.mjs`, `test/packages/ui-remote-chat-context.test.mjs`, `test/packages/agent-prompt-context.test.mjs`, `test/contracts/chat-placement.test.mjs`, `test/contracts/chat-placement-registry.test.mjs`.

## Room

`@hachej/boring-agent/room` is a shared room of people and agents on one pi-durable session that never runs a model (the Studio channel plan, boring-factory#566). Conversations are named (`main`, `admin`, `agents:<a>:<b>`); `createRoom({ harness, context })` maps each name to a native conversation on first use.

- **Entries.** Seven kinds (`room.message`, `room.removed`, `room.card`, `room.pin`, `room.question`, `room.action`, `room.system`); every `data` names its `author`. `write(name, { requestId, kind, data }, { people, agents })` appends the entry, its native passive-write record (`type: 'write'`, `status: 'done'`, keyed by the writer-namespaced `requestId`) and the wakes it causes in one `harness.commit`. The same `requestId` again returns the first entry and wakes nobody; `Conversation.submit` with that id sees the same record.
- **The view.** `roomView(entries, cards, viewer)` is a pure fold: a removed message reads « message supprimé » without attachments, a question is `answered` once a message replies to it, a card shows the state the host passes in. The cursor is the last entry id; `entries(name, after)` resumes after it.
- **Who answers.** `wakeFor(entry, room)` is pure: mentions wake at most two agents, a reply wakes the agent replied to, a reply to a question answers it (`{ kind: 'answer' }`, not a new turn), and an unaddressed message wakes `agent:pm` only when its sender is the only person in the room. Agents never wake each other in `main`; in `agents:<a>:<b>` (`agentsConversation(a, b)`) each message wakes the other agent, and the sixth turn returns `{ kind: 'capped' }`. A person's card action wakes the card's agent; platform changes wake nobody.
- **Wakes.** An open wake (`boring.room.wakes`) is closed by the agent's `settle(agent, wakeId, reply)`, a `room.message` keyed `wake:<wakeId>`; without an open wake for that agent nothing is written. `resend()` is the alarm's step: a wake open for two minutes is resent with doubling backoff, at most five times. After that the room closes it itself as `platform:room` with one « Je n'ai pas pu répondre. Réessayez. » message under the same key, so a late reply adds nothing.
- **The agent's side.** `createRoomTurn({ conversation, context, port })` runs in the agent's own home, lifted from the WhatsApp gateway: `wake({ wakeId, input })` records the owed settle, submits `room:<wakeId>` with `whenBusy: 'followUp'`, relays frames (`port.stream`) and new `ask_user` questions (`port.question`) from `conversation.watch`, and calls `port.settle` with the answer text. A resent wake finds its submission by `requestId` and settles again without a new run. `start()` after `harness.resume()` settles what a crash left owed; `answer(callId, text)` feeds a room reply into the pending `ask_user`.

Membership, roles, rates, spend and the doors stay with the host, which checks them before calling. Tests: `test/packages/agent-room.test.mjs`, and `test/contracts/room-crash.test.mjs` (SIGKILL mid-run, before and after the settle).

## Chat over a hibernatable WebSocket

`createConversationSocketHandler` (from `@hachej/boring-agent/chat-transport`) serves the chat transport over WebSockets accepted with the Durable Object Hibernation API, so an idle open page does not keep the object in memory (or billed). One socket carries the watch (the same `view` then `ops` frames as the NDJSON stream) and every call: `{"kind":"call","id","op","params","body"}` is answered by `{"kind":"reply","id","status","body"}` and runs through `createChatTransportHandler` unchanged (validation, `allow`, `project`, `submission-refused`, request-id deduplication). A submit without `whenBusy` is a follow-up when the conversation is busy. `ping` is answered `pong` (on Cloudflare by `setWebSocketAutoResponse`, without waking the object).

Mount it in a Durable Object (any host with the same `acceptWebSocket`/`getWebSockets` and attachment methods works the same):

```js
sockets = createConversationSocketHandler({ state: this.ctx,
  // Upgrade only: who and which conversation, kept in the socket's attachment (`serializeAttachment`). Null answers 401.
  authenticate: async request => ({ owner: personOf(request), conversationId: selectedIn(request) }),
  // From the attachment alone, at accept and after every wake: the same access the HTTP handler gets.
  access: async ({ owner, conversationId }) => ({ conversation: await open(owner, conversationId), context }) });
fetch(request) { if (request.headers.get('upgrade') === 'websocket') return this.sockets.fetch(request); /* ... */ }
webSocketMessage(socket, message) { return this.sockets.webSocketMessage(socket, message); }
webSocketClose(socket, code, reason) { return this.sockets.webSocketClose(socket, code, reason); }
alarm() { void this.sockets.resume(); /* ... */ } // or Lifecycle's host `onStart`
```

After a wake the in-memory watches are gone; `resume()` (also run by every message and upgrade) reopens each socket's watch from its attachment and sends a complete view first. `broadcast(event, { owner?, conversationId? })` sends host events (`{"kind":"event","event"}`: presence, the conversation list) on the same sockets, and `connections({ owner?, conversationId? })` lists the open sockets' attachments. A browser cannot set headers on a WebSocket: a client offers `boring.chat` as subprotocol (the handler selects it) and a bearer host reads its credential from another offered value, as the Cloudflare recipe does. Pi keeps idle documents and contexts in memory on ten-minute timers by default, and a pending timer keeps a Durable Object from hibernating: open the harness with `settings: { documentRetentionMs: 0, contextRetentionMs: 0 }`.

The client is `createRemoteChat({ transport: 'websocket' })` (or `useRemoteChat({ transport: 'websocket' })`): the controller API is unchanged; unanswered calls are sent again unchanged (same request ID) on the next socket, each socket starts from a complete view, and if the first socket cannot open it uses HTTP. Reused from Cloudflare: the platform Hibernation API itself; the agents SDK `WebSockets` capability (`agents/websockets`) was not used because it is a Lifecycle catch-all that claims every upgrade and speaks the Agent protocol, while this handler must mount in a plain Durable Object too. `PiHarness` leaves "how a session reaches a client" to the host. Tests: `test/packages/agent-chat-socket.test.mjs`; the recipe journey `examples/hosts/cloudflare/journey.mjs` (`CF_HIBERNATION=1` proves hibernation with the socket open).

## Native questions

`createQuestions` from `@hachej/boring-agent/questions` exposes a native task, session document family and extension. Install the extension explicitly. Call `admit(tx, question, ownership, context)` in a native commit to persist a single-choice question and its task together. `resolve` and `consume` take the caller's native transaction so host writes can share that atomic commit. Call them before host table writes: native task reads after a table write are unavailable and the operation returns conflict. Host authentication and current subject/policy checks run at both boundaries. A resolved answer is clarification, never publication permission.

The question task runs its durable wait phase while observing the native document. Parents can park with native task waiting on its ID. No browser or process-local waiter registry owns the answer. Native shutdown cancels observation; reopening checks the retained document. Session documents retain resolved/cancelled evidence after task completion. Expiry changes only pending state; late consumption refuses without deleting a prior answer. If supplying a custom clock, use the same clock for the Harness. Raw native document access is trusted host access; remote question resolution is still pending.

## Validated document delivery

`createDocumentDelivery` from `@hachej/boring-agent/delivery` admits a producer callback and its delivery task in one native transaction. The callback creates ordinary native tasks and returns `TaskId<string>`. Delivery captures the document precondition and authenticated identity before production, waits on the native producer, validates its actual string output and persists that exact text before publication. Host validator versions and operation namespaces must remain stable across recovery.

This is string validation and conditional Markdown delivery. It does not implement model repairs, arbitrary host record delivery or prove tool provenance. Supply both `ResourcePublisher` and `PublicationLookup`. Recovery defaults to lookup only after durable publication intent; a missing receipt stays unknown. Explicit `replay: 'safe'` requires host qualification of durable duplicate suppression. Abort means the native task stopped; an interrupted external publication can still require lookup under the admitted operation ID.

The admission target can include `preconditions: readonly ResourceExpectation[]`. Use these for source-owned generation and human-edit revisions that must still match when output is published. Admission copies and validates the target and conditions before awaiting producer creation. The provider checks the guards in the same transaction as the document change; delivery includes them in its receipt digest. Independent subjects can use independent guards.

```ts
await conversation.commit(tx => delivery.admit(tx, createProducer,
  { kind: 'absent', target: report, preconditions: [generation, humanEdit] },
  { ownership: { kind: 'conversation' } }, context), context);
```

The native delivery task is version 2. Existing version 1 records migrate with empty guards and unchanged producer, identity, target, namespace, validation version and checkpoint. Downgrading to a version 1 definition refuses guarded version 2 work. A committed receipt remains the result of that original delivery after a guard advances; a guard change before publication causes conflict. Advancing a provider guard and admitting native tasks are still two separate transactions. Hosts need recovery for that boundary; this API does not make them atomic.

`resolveAccess` may return a Promise. When recovery reads the original actor from native producer input, pass that already-authenticated access as the sixth admission argument: `admit(tx, createProducer, target, taskOptions, context, access)`. Admission captures its identity before awaiting producer creation. Publication still resolves current access and compares the original identity. Omitting the sixth argument preserves resolution during admission; such a resolver must not read the same Harness or call `tx.task` after producer writes. Native transactions reject table reads after their first write. Explicit access is trusted host input, not authentication or a grant. Resolved credential fields are copied before digest, memo and provider awaits.

## Authorized conversation text

`createConversationProjectionHandler` from `@hachej/boring-agent/projection` returns a Fetch `Request` to `Response` handler. The host authenticates the request and supplies the original native conversation, Context, fixed runtime/scope/principal binding, current authorization callbacks and a revocation signal. Requests use GET with `?version=2`. Other versions return 426 and other methods return 405. No command or asset route is installed.

The response is newline-delimited JSON with `boring.conversation-text` version 2 frames. The first frame is a bounded snapshot; subsequent frames contain changed rows and the complete bounded row order, or a replacement snapshot when that is smaller. A delta names its preceding frame. Connection ID, frame and observation time describe this observation only; they are not native durable cursors. The stable row key is the original conversation ID, entry ID and message index. Rows absent from a delta's order are removed.

Only host-permitted user/assistant text blocks are selected. Entry data, system instructions, thinking, tool arguments/results, assets, Context and errors are excluded. Live generation is also excluded; entry permission does not authorize the private live document. Entries retain their original conversation IDs across forks so entry policy can distinguish inherited content. This projects raw retained entry text, not edited model-context reconstruction.

`CONVERSATION_PROJECTION_LIMITS` fixes the window at 200 messages, each at most 32 KiB, with at most 192 KiB of messages and a 256 KiB frame. Byte limits measure UTF-8 JSON, including escaping and metadata; the frame limit includes its newline. Selection uses the pinned native entry-ID recency, then restores native presentation order, including its head marker. Oversized text is clipped at scalar boundaries and marked `clipped`. `window.truncated` reports omitted older permitted rows without counting denied entries. These limits bound adapter retention and wire output, not native watch allocation or the cost of scanning entries for permission.

Authorization must return literal `true` at opening, after watch acquisition and before each candidate delivery. The synchronous entry policy must also return literal `true`. Abort the host signal on revocation or identity change, including idle periods. Policy changes without a native update require revocation and a fresh connection. No further payload is enqueued after abort; delivered bytes cannot be recalled. The browser integration must clear restricted presentation on close/identity change while preserving separately owned drafts. That browser integration is not implemented here.

The adapter keeps the last bounded delivered window and no update queue. A slow reader observes the latest permitted view when it pulls. Unchanged visible rows produce no frame, including configuration-only updates. Disconnect stops only this connection's native watch. Reconnect authorizes a new watch and snapshot without submitting work. End of stream means observation ended, never confirmed task termination.

`createConversationTextReceiver(expectedIdentity)` validates one complete JSON frame per `read(line)` call and returns a detached snapshot. It rejects unknown fields, invalid bounds, identity mismatches, connection changes, missing bases, duplicate keys and sequence gaps. Any failure clears its cache and requires a fresh initial snapshot. Call `reset()` when opening a new connection or ending restricted presentation. The receiver does not frame network chunks, own a socket or reconstruct native execution state.

TLS, cookies, CORS, socket/proxy lifecycle, browser presentation and deployment authentication remain host qualifications. Public projection tests exercise actual native watches through in-process Fetch/Web Streams. `npm run test:projection-consumer` installs the agent archive without files/UI/execution packages, checks strict declarations, repeats the tests and builds the receiver for a browser. It requires the pinned registry archives in a writable npm cache.

## Pinned JSON definitions

`loadAgentDefinition` from `@hachej/boring-agent/definitions` reads an authorized exact resource revision and returns a native `AgentChange` plus an `AgentDefinitionBinding`. Install `@hachej/boring-files` for this optional subpath. Importing the loader does not load the native engine or UI packages.

The JSON resource contains exactly these fields:

```json
{"format":"boring.agent","version":1,"instructions":"Use the installed document tool.","tools":["save_note"]}
```

The host supplies the reader, exact `ref`, authenticated `access`, host implementation version and a `resolveTool(name)` callback. ```

Persist it in host-owned or native storage when the workflow requires reproducibility. On reload, pass it as `expectedBinding` and resolve current permissions again. The host chooses whether to migrate a changed definition or refuse that workflow.

Hosts requiring reproducibility must check versions and current authorization at admission and recovery.

## One-call runs

A run is one agent asked once, in its own native conversation, for a result: the host starts it by a key, the agent answers by calling a result tool (or in text), the host checks the answer, asks for a corrected one while the repair budget lasts, and hands the end to the operation that started the run. Every home needs the same parts, so they are here once. Pi still owns the turns, the transcript and recovery; these read the transcript and submit native follow-up inputs, and the host keeps its data and its budgets.

- `@hachej/boring-agent/run-result` (optional peer `typebox`): `resultConfig` (the card's `result: { schema?, validate?, repairs? }`), `resultParameters`, `resultExecutor` (the result tool's `execute`: checks the call against the schema and the card's validator operation, spends the budget), `settleResult` (wait for the answer, read it, repair it in the run's own conversation with `repair:<conversation>:<n>` inputs, check it once more with `phase: "delivery"`), `runMessage`, `runResult`, `resultState`, `evidenceOf`, `withEvidence`. The validator is an operation the host calls through `invoke(operation, input, key)` as the person whose run it is. `ResultBudget` keeps the stored document shape of the homes that ran this first.
- `@hachej/boring-agent/runs`: the run ends (`completed`, `invalid_output`, `cancelled`, `interrupted`, `revoked`, `error`), `RunView`, `sumUsage`, `OVER_BUDGET` and `isOverBudget`, and `deliverRunEnd`: bounded attempts under one `deliver:<key>` receipt key, a completed end checked again first and delivered as `invalid_output` when it no longer passes. A delivery that fails is reported, not dropped.
- `@hachej/boring-agent/run-ledger`: `createRunLedger(sql)` keeps `_host_agent_runs` in the person's own SQLite file; an end happens once (`UPDATE ... RETURNING`), so a cancel and the run's own end can race. `createRunner({ ledger, person, context, has, prepare, invoke, admit?, usage? })` gives `start(agent, input, key, deliverTo)` (the same key is the same run), `status`, `cancel` and `recover`: a run a stopped process left ends `interrupted`, and one that ended without being delivered is delivered. `admit` is the host's spend meter: a refused run is never started and ends `error: over_budget`. The cap, the spend ledger and the prices stay the host's.
- `@hachej/boring-agent/run-outbox`: `stageStarts(sql, ...)` in the app operation's own transaction, `drainStarts` after the commit. A row is removed only when the run is acknowledged, retried with backoff when it may pass, dropped when it never will.

Stores are a synchronous `SyncSql` function (`node:sqlite` `prepare(sql).all(...params)`, a Durable Object's `sql.exec`); nothing here opens a connection or a transaction. Not here, by design: the card parser and its front matter, the app operations a run calls, the schedule and alarm of a Durable Object home, and anything clinical or app specific.

## Structured output and native tool evidence

`@hachej/boring-agent/validation` exports `createOutputValidation`. Install its native extension explicitly. A producer returns `{ text, evidence }`, where `evidence` contains retained native tool-result entry IDs. Create the returned validation task with `{ producer }` through ordinary `tx.createTask`; it waits for the producer and returns `valid`, `invalid` or `producer-failed`. Only a `valid` result may feed application delivery. The host supplies a stable task name and definition version; incompatible stored versions require native migration or refusal.

The shared `check` method is also useful in `GenerationHooks.onYield` to request a bounded native continuation. Hook errors are observational. Always run the separate final validation task against the completed producer, even when the hook previously accepted an answer. Repair counts are application decisions, distinct from provider retries and compaction.

Validation borrows the host Harness through `harness: () => harness`. It reads native records in one read-only transaction, then calls the host's `authorize` and `validate` functions outside that transaction. Authorization must return literal `true` before and after validation. Inputs and the validated JSON value are detached before later awaits; validators cannot return undefined, non-finite numbers or non-JSON objects. Throws and missing evidence refuse validation.

Each evidence entry must link to a completed native ToolTask, its original assistant call and the original producer's ownership subtree. Task-owned conversations count; inherited fork history and sibling work do not. This bounded adapter accepts 1–64 distinct results and traverses at most 128 ownership edges per result. Every diagnostic currently refuses evidence, including informational truncation/spill notices. The host still checks tool semantics, current access and completeness; a silent truncation inside a custom tool cannot be inferred from native records.

`NativeToolEvidence.call.arguments` contains the model's original call. Native argument preparation and tool hooks can change executed arguments. Tools requiring exact normalized-input provenance must retain those inputs with their actual return. This adapter proves the retained return and native call/task relationship, not exact executed arguments, external-source truth or nested code-mode evidence.

## Asking the person

`@hachej/boring-agent/ask-user` exports `createAskUserTool()`, a replay-safe native tool named `ask_user` with arguments `{ question, options?: string[2..6], allowFreeText?, questions?: { question, options? }[1..8] }`. Free text is accepted unless `allowFreeText` is `false`; `questions` makes one form answered as one free text that lists each question and its answer (the `pi-chat` question card renders it). The call waits on a conversation document keyed by its assistant entry and tool call ID, so no model request is held, a pending question survives a restart and stopping the conversation cancels it. A trusted host resolves it with `answerUserQuestion(conversation, askUserQuestionId(assistantEntryId, callId), answer)` (pass the scoped ID through `ChatTransportAccess.answer` after authenticating the person): the answer must be an option when `allowFreeText` is `false`, at most 2000 characters; one answer wins, repeating it is idempotent. ## Browser tasks

`@hachej/boring-agent/browser-task` exports `createBrowserTaskTool({ name, description, parameters, checkAnswer, maxAnswerBytes? })`: the same durable wait as `ask_user` (shared internally), answered by the person's open page with a JSON object instead of a short text. The page finds the call in the conversation it watches (a call of that tool with no result yet) and answers through the chat transport's `?op=answer` with `browserTaskId(assistantEntryId, callId)`; the host wires `answerBrowserTask(conversation, tool, id, answer)` there after authenticating the person. It is gated by `allow('configure')` and delegated to `ChatTransportAccess.configure(change)`; without that function the op answers `not-supported`. A change applies from the next model request.

The skills section (`staticSkills` and `liveSkills`) tells the model that a user message starting with `/<skill-name>` is an explicit request to load that skill first, which is what the chat's `/` menu inserts. `defineAgent(...).skills` lists each skill's name and description for such a menu when the skills are an array.

With self-evolution, workspace skills may be flat `.agent/skills/<name>.md` files or `.agent/skills/<name>/SKILL.md` folders. Only `SKILL.md` defines a skill inside a folder; other Markdown and deeper files are companions, not skills. `load_skill` returns the body followed by “This skill's folder is `.agent/skills/<name>`; paths in it are relative to that folder.” (For flat files the folder is `.agent/skills`.) A skill can say `see portions.md` or `see tables/2026.csv`; the agent reads that path under the returned folder with Pi's native `read`, through the same workspace provider. Scanning and loading do not read the companions. No special companion folder, new file tool or additional access is granted. Host-given `Skill` data stays `{ name, description, body }`: with no source folder, `load_skill` returns its body unchanged.

## Live skills

`staticSkills(skills, { name, intro?, visible? })` takes an array and returns `{ extension }`. `liveSkills(source, { name, maxAgeMs?, onDiagnostics?, companionFiles?, onPublish?, intro?, visible? })` takes a `SkillSource` instead, so skills added, edited or removed after start reach the agent without rebuilding the extension; `defineAgent({ skills })` takes either. A source is `{ list(context), version(context) }`: `list` returns `{ skills, errors }`, `version` a cheap token that changes when the skills do. Two are built in, and both read through the workspace's Pi `FileSystem` (an `ExecutionEnv` is one; pass the workspace provider's instance, never `node:fs`):

- `directorySkillSource(fs, 'skills')`: every `skills/<name>/SKILL.md`, its folder passed to `load_skill` as for self-evolution; `{ flat: true }` adds every `skills/<name>.md` file (self-evolution's `.agent/skills` layout). A missing directory holds no skills; folders without `SKILL.md` are skipped, and companion files are read only with `companionFiles` (below). Its version is each skill file's path with its `mtimeMs` and size (one `listDir` and one `fileInfo` per skill file).
- `fileSkillSource(fs, 'notes/triage.md')`: one skill file, its folder the file's directory; a missing file holds no skill. Its version is the file's `mtimeMs` and size.

The source is read on first use. After that the listing section and `load_skill` use the cached copy until it is older than `maxAgeMs` (default 5000), then ask `version()` and read `list()` again only when it changed. There is no watcher or timer: the check happens on use, and concurrent uses share one read. `load_skill` asked for a name the conversation's listing does not hold makes the same check at once, whatever `maxAgeMs` (see *refresh on miss* below). What a source returns is checked with `validSkill` and the duplicate-name rule (the first skill of a name wins). A skill that fails, or a file that cannot be read or parsed, is left out instead of taking the extension down: `onDiagnostics(errors)` receives every `SkillError` (`{ path, name?, message }`) after each read (an empty array once all are fine), and `load_skill` asked for the left-out name answers `Skill "<name>" could not be loaded (<path>): <reason>`. A source whose `list`/`version` throws is a host bug: the section keeps the text already shown (Pi's `renderSections`) and `load_skill` fails. A fixed array works as before: validated once, an invalid or duplicate skill throws. With no skills, the section is omitted.

Pi renders every extension section before each model request (`PromptSection.render`), so a refreshed listing reaches the next request; Pi's `planSystemEntries` writes nothing when the text is unchanged and a minimal `pi.system` section patch when it changed. Prompt cache: on a model that accepts system messages mid-conversation the patch is appended and the cached prefix stays valid; on one that does not, Pi collapses the system messages into one leading prompt, so every listing change rewrites the start of the prompt and misses the provider's prompt cache once. Keep `maxAgeMs` coarse and edits to skill descriptions deliberate. Pi itself has no skills loader in the packages this one depends on (`pi-durable` and `pi-ai`), so this is a host concern built on its `FileSystem` and section seams.

**Control (all optional; with none set, the extension behaves as above).**

- `visible(conversationId, skills)`: which skills a conversation sees. It is called once per render and once per `load_skill` call (may be async) with the whole current list of valid skills, and returns the subset that conversation sees (matched by name). The id is Pi's own: the section gets it from `PromptInput.conversationId`, the tool from `ToolExecutionApi.conversationId`, so no host bookkeeping is needed. A hidden skill is left out of the listing, and `load_skill` answers for it exactly as for an unknown name (`Unknown skill "<name>". Available: <visible names>`). With a filter, a skill that could not be read also answers as unknown (it is never in the list); its reason still reaches `onDiagnostics`. Works for `staticSkills` too.
- `companionFiles: true`: `load_skill`'s answer ends with the files beside the skill's `SKILL.md` (the Agent Skills layout: `references/`, `scripts/`, `assets/`; any depth, name order, at most 200), and `load_skill({ name, path })` returns one of them as text. The files are checked when the listing is read, and a listed file is checked again when the model asks: each one must be a regular file inside the skill's folder that reads as UTF-8 text. A symbolic link, an unreadable or binary file (a NUL byte or invalid UTF-8) and files past the 200th are left out and reported to `onDiagnostics` (`{ path, name: <skill>, message: 'Companion file left out: …' }`). Only a listed path is read, so a path cannot leave the folder (`../`, absolute paths and links are refused with `Skill "<name>" has no companion file "<path>"`). Before returning a listed file, `load_skill` looks at the skill's folder, every folder on the way and the file with `fileInfo` (which does not follow links) and checks the text again: a file or folder swapped for a symbolic link since the listing (the agent may write its own skill folder) answers `Companion file "<path>" of skill "<name>" could not be read: <path> is a symbolic link` and is never followed. The list is kept with the listing: a companion added or removed later shows up on the next read of the source (a `SKILL.md` change or `refresh()`); a listed file's content is read on demand through the source's `fs` (the same workspace `FileSystem`; both built-in sources set `SkillSource.fs`), never cached. A skill file not named `SKILL.md` (a `fileSkillSource` on `notes/triage.md`) has none. A source without `fs` throws.
- `intro`: the listing section's text before the `- name: description` lines, replacing the default (“Before starting a task that matches a skill, call load_skill …”, with the `/<skill-name>` rule). The skill lines still follow it.
- `onPublish(next, previous)`: called with both listings' skills before a newly read listing of a source replaces the current one (may be async). Return a reason, or throw, to refuse it: the current listing stays and `onDiagnostics` gets that listing's errors followed by `{ path: '', message: 'Listing refused by onPublish: <reason>' }` (the per-skill errors are kept; the entry with `path: ''` is the refusal). A refused listing is not offered again until the source's version changes or `refresh()` runs. The first read is offered too (`previous` empty).
- `liveSkills(source, options)` returns `{ extension, refresh }`; `staticSkills` returns `{ extension }` only. `await refresh(context)` reads the source now, whatever `maxAgeMs`, and publishes it through `onPublish`; `refresh(context, name)` takes only that skill from the new read (added, replaced or removed) and keeps the others as they were until the source's `version()` changes again: later `maxAgeMs` checks and `load_skill` misses do not re-read an unchanged source, and the first read after a change offers the whole source (through `onPublish`) as usual. A source only lists everything at once, so the others' pending edits are part of that next read. It resolves `true` when published, `false` when refused. Reads run one at a time, so a refresh never interleaves with a `maxAgeMs` check. Call it from the code that changed the skills (an editor save, a self-evolution keep); there is still no watcher.

**Refresh on miss.** On a source, `load_skill` for a name not in the conversation's listing checks the source once before answering, whatever `maxAgeMs`: `version()` now, and `list()` plus `onPublish` only when the version changed, serialized with the other reads. So a skill written a moment ago loads on the first try, and the listing shows it from the next request on. A model guessing names costs one `version()` per miss (a `fileInfo` per skill folder for the built-in sources), never a re-read of an unchanged source, and concurrent misses share one check in flight, so there is no time floor. A miss of a refused listing's skill stays a miss until the version changes or `refresh()` runs, as above.

```ts
const skills = liveSkills(directorySkillSource(env, 'skills'), {
  name: 'workspace.skills',
  companionFiles: true,
  visible: (conversationId, skills) => billingConversations.has(conversationId) ? skills : skills.filter(skill => !skill.name.startsWith('billing-')),
  onDiagnostics: errors => errors.forEach(error => log.warn(`skill ${error.path}: ${error.message}`)),
  intro: 'Clinic procedures. Load the matching one with load_skill before you answer:',
  onPublish: next => next.some(skill => !skill.body.includes('Reviewed')) ? 'unreviewed skill' : undefined,
});
const agent = defineAgent({ id: 'clerk', model, extensions: [skills.extension] });
await skills.refresh(context, 'letters'); // after the host saved skills/letters/SKILL.md
```

### Versioned skill folders

`directorySkillSource(fs, root, { versioned: true })` reads skills published as whole versions, for example from a bucket mounted read-only into the agent runtime (the library only reads a folder through the workspace `FileSystem`; it does not know where the bytes live):

```
<root>/v12/<skill>/SKILL.md   (+ companion files)
<root>/v13/<skill>/SKILL.md
<root>/current                one line: v13
```

- **Publish**: write the new version folder completely, then overwrite `current` with its name. A version folder is never changed once written (the library reads each version once and keeps it).
- **Rollback**: write the old version's name back into `current`.
- **Which version a conversation sees**: a new conversation starts on the version `current` names (read again once older than `maxAgeMs`). A running conversation keeps the version it started on until the person sends `/reload-skill`, which moves that conversation only to the version `current` names now (reading that version's folder again). `{ flat: true }` applies inside each version folder.
- **A bad pointer**: `current` missing or unreadable, a value that is not one folder name (`../v1`), or a version with no folder is reported to `onDiagnostics` as `{ path: '<root>/current', message }`; new conversations stay on the last good version, and `/reload-skill` answers `Skills stay on version <v>: <message>`. Before any good version, the agent has no skills.

`/reload-skill` is the skills extension's native tool `reload_skill` (Pi extension point: a tool and the listing section of the extension, over the `SkillSource` on the workspace's `ExecutionEnv` `FileSystem`; no second loader). The listing tells the model that a message `/reload-skill` means calling it, as `/<skill-name>` means `load_skill`; the tool answers `Skills reloaded: version <v> (<names>).` A host command can do the same without the model: `refresh(context, undefined, conversationId)` moves one conversation, `refresh(context)` every conversation, and resolves `false` on a bad pointer. `refresh(context, name)` is refused (versions move whole), and so is `onPublish`. Limit: which version each conversation is on is kept in the process, so after a restart every conversation starts on the version `current` names then.

```ts
const agent = defineAgent({ id: 'clerk', model, skills: directorySkillSource(env, '/mnt/skills', { versioned: true }) });
```

## Sub-agents and schedules

These follow [Pi Durable on Cloudflare](https://earendil.com/posts/pi-durable-on-cloudflare/) and stay host-agnostic: a Node process and a Durable Object mount the same tools.

**Delegate.** `createDelegateTool({ agent, name?, description?, onChild?, limits?, meter?, childTools? })` from `@hachej/boring-agent/agents` is Pi's documented subagent pattern (pi-durable README, "Abort and Subagents"; pi-durable ships it as an example, not an export) as a tool factory. `delegate({ task })` creates a child conversation owned by the calling tool task (`ownership: { kind: 'task', taskId }`), configured as the child agent alone (its extensions, model and instructions; the inherited tool filters reset), submits the task with request id `<name>:<taskId>` and returns only the child's final text, with `details` (`DelegateDetails`, below) naming the child. It is replay-safe: a rerun after a crash or eviction finds its child through Pi's ownership index (`scanConversations({ ownerTaskId })`) and its submission through the request id, so it never starts a second child or turn. Aborting the call aborts the child. With `defineAgent`, declare `delegates: [{ agent: researcher }]`: each becomes a tool of the agent and `install(registry)` installs the child's extensions as well. A raw-Pi host installs the child agent's extensions itself.

**Child identity.** The kit copies no identity onto a child; the host decides what a child carries. Pass `onChild(parent, child, tx)` in `DelegateOptions` (or a `delegates` entry): it runs inside the same native commit (`ToolExecutionApi.commit`, Pi's `Tx`) that creates and configures the child, so the child never exists without what it writes, and a throw aborts the commit and leaves no child (the delegate call returns an error). It runs once per child, not on a replay that finds the existing child. Read and write only through `tx`:

```ts
const delegates = [{ agent: researcher, onChild: async (parent, child, tx) => {
  const from = await tx.doc(HostIdentity, parent), to = await tx.doc(HostIdentity, child); // HostIdentity: the host's conversation doc
  to.user = from.user; to.workspace = from.workspace; to.permissions = [...from.permissions];
} }];
```

**Sub-agent card data.** Every delegate call's `details` is a stable `DelegateDetails` (exported from `@hachej/boring-agent/agents`, with `DELEGATE_DETAILS_KIND` and `DelegateStatus`): `{ kind: 'boring.delegate', version: 1, agent, conversationId, status, startedAt, durationMs, toolCalls, tokens: { input, output }, error? }`. `status` is `running`, `done`, `failed` (with `error`, the same text as the result) or `cancelled`; `conversationId` is the child conversation, `toolCalls` counts the tool calls in the child's assistant messages and `tokens` sums the child's `UsageDoc` (input includes cache reads and writes). While the child runs, the tool publishes `running` values through Pi's `api.details`, so they appear in the call's `LiveDoc` tool slot: it watches the child's `LiveDoc` (`api.watchDoc`) and, when a step of the child's run changes, recounts (`tx.scanEntries` from the last counted entry, `api.snapshot(UsageDoc)`) and publishes only when the counts change; Pi paces the commits. The final result carries `done`, `failed` or `cancelled`. When the delegate call itself is stopped, Pi writes its aborted result from the slot, so its details keep the last `running` value: read `running` on a settled error result as `cancelled`. The `pi-chat` block's `SubagentCard` and `parseDelegateDetails(details, result?)` do this and render any call carrying these details.

**Delegate limits, meter and child tools.** Host policy, all optional in `DelegateOptions` (or a `delegates` entry); Pi has no extension point for running-child limits, start rates or a host meter, so the tool enforces them itself (BORING-PI-4: host concern). With none set the tool behaves as above.

| Option | Type | Effect |
| --- | --- | --- |
| `limits.maxRunningPerConversation` | `number` | Children running at once for one parent conversation. |
| `limits.maxRunning` | `number` | Children running at once across every parent conversation, for the delegate tools sharing this `limits` object in this process. |
| `limits.maxStartsPerHour` | `number` | Children started for one parent conversation in the last 60 minutes (rolling), ended or not. |
| `limits.maxTaskChars` | `number` | Characters of `task`. |
| `limits.timeoutMs` | `number` | Wall-clock milliseconds from the call's first start (kept across a rerun). On expiry the tool aborts the child conversation (`ConversationHandle.abort`, the same cancel path as a stopped call) and the call fails: `details.status` `failed`, `error` `The <agent> agent timed out after <ms> ms.` |
| `meter` | `(parent, child) => DelegateMeter \| Promise<DelegateMeter>` | The host's handle for the child's spend: the tool calls `record(event)` once per child model response (`DelegateModelEvent`: `entryId`, `provider`, `model`, Pi's per-response `usage`) and `close(end)` once at the end (`done` once the child's answer is committed to the parent; `cancelled` only when the call or the child was aborted; `timeout`; `failed` for every other end, including a throw such as a failed commit). The kit keeps no log. |
| `childTools` | `string[]` | Names of the tools a child may have: its enabled tools are the intersection with what it would otherwise get, written as Pi's own `pi.agent` `tools` filter in the creating commit. |

A call over a limit is refused: it creates no child and returns an ordinary error result the model reads, for example `2 delegates already running for this conversation (limit 2).`, `1 delegate already running across the conversations sharing this limit (limit 1).`, `1 delegate already started for this conversation in the last hour (limit 1).` or `The task is 41 characters; the limit is 40.` It never throws and carries no `details`. Only a call that would create a child is checked: a rerun that finds its existing child (after a crash or eviction) is never refused, and a call counts once, by its tool task.

The counts live in this process and belong to the `limits` object: every delegate tool given the same object shares them, so one object passed to several `delegates` entries is one host-wide cap, while two entries written with their own literals (`limits: { maxRunning: 2 }` each) get two separate budgets; the refusal text says “sharing this limit” for that reason. Separate processes do not share them, and a restart starts them empty (reruns that reattach count their children again; the hourly window forgets earlier starts). `meter` is called after the commit that creates the child and again by a rerun in a new process that reattaches to it, since the earlier handle is gone; such a rerun sends the child's earlier responses again, so dedupe by `entryId`. A throw from `meter` fails the call; a throw from `record` or `close` is ignored.

```ts
const limits = { maxRunningPerConversation: 2, maxRunning: 8, maxStartsPerHour: 20, maxTaskChars: 4000, timeoutMs: 300_000 };
const delegates = [
  { agent: researcher, limits, childTools: ['search', 'read_file'], meter: (parent, child) => flightLog.open({ parent, child }) },
  { agent: writer, limits }, // same object: shares the host-wide cap of 8
];
```

**Schedule.** `@hachej/boring-agent/schedule` exports `createScheduleExtension({ now?, onDeadline?, maxDelaySeconds? })`, one native extension with `schedule({ instruction, delaySeconds | at, operationId? })`, `list_schedules()` and `cancel_schedule({ id })`, plus the delivery task `ScheduledDelivery`. A schedule is a native Pi task owned by the conversation as background work: it sleeps on the Harness clock (`runtime.sleep`) and then submits the instruction to its conversation as a follow-up input (entry kind `boring.schedule.delivery`, request id = schedule id, so a replayed delivery never submits twice). Pi's scheduler runs it and a restart resumes it; there is no second scheduler. Pending schedules live in the conversation document `ConversationSchedules`, so a conversation lists and cancels only its own; a cancelled schedule's task wakes and ends without delivering. `schedule` is idempotent on `operationId` (default: the tool task, so a replayed call returns the schedule it made). Hosts schedule outside a tool with `addSchedule(tx, conversationId, { operationId, instruction, runAt })`, `cancelSchedule(tx, conversationId, id)` and `listSchedules(harness, conversationId, context)`. Pass the Harness's own clock as `now`. A host with one wake-up timer (a Durable Object alarm) computes the earliest deadline from `harness.inspect()` with `scheduledDeadline(task)` and moves the timer earlier from `onDeadline`; its alarm handler only reopens or resumes the Harness, and Pi delivers what is due.

**Storage conformance.** Boring ships no Pi `Storage` implementation. `test/packages/pi-storage-conformance.test.mjs` runs Pi's own suite (`createStorageConformance`, what `registerStorageConformance` registers with Vitest) on every storage the repository configures: `openPiStorage` (shared/pi-storage.mjs) on the local-disk and network-file-system presets, Pi's `SqliteStorage` over `openBrowserSqlite`, and Pi's `openDurableObjectSqliteStorage` on a SQLite-backed Durable Object in workerd through miniflare (the version the pinned wrangler resolves).

## Tools from a JSON Schema

`jsonSchemaTool({ name, description, parameters, execute, ... })` from `@hachej/boring-agent/agents` makes a native tool registration from a raw JSON Schema (an MCP server's `inputSchema`, an agent-written `.agent/tools/*.json`) with typebox's `Type.Unsafe`, so no `as unknown as TSchema` cast is needed. It refuses a schema that is not `"type": "object"` and adds an empty `properties` when there is none. It validates nothing itself: the Harness already validates every call's arguments against `parameters` before `execute` (Pi's `validateToolArguments`, which compiles plain JSON Schema with typebox) and answers a mismatch with an `invalid_arguments` error result naming the fields, before an approval gate is asked. The studio's MCP recipe and self-evolution use it; their journeys send one call with a missing required argument each.

## Self-evolution

`defineAgent({ …, selfEvolving: true, workspace })` lets the agent keep its own standing instructions, skills and tools in the `.agent/` folder of its workspace and apply them with a `reload` tool; the plan and its reasons are in [SELF-EVOLUTION.md](../../docs/architecture/SELF-EVOLUTION.md). Off by default.

- One native extension per workspace, named `self-evolving:<workspace>`, so two workspaces in one host never replace each other's tools. Without a fixed `workspace` the agent works in a workspace per conversation: `inWorkspace(name)` returns the agent of workspace `name` (made once, then the same), whose configuration selects only `self-evolving:<name>`; the host creates each conversation with the agent of its owner's workspace and installs and reloads that workspace's extension when the workspace opens, so one harness and one registry never offer one workspace's agent-written tools to another's. It carries the skills (the host's, then `.agent/skills/*.md` and `.agent/skills/<name>/SKILL.md`, read with `directorySkillSource(env, '.agent/skills', { flat: true })`, behind the usual `load_skill`), `reload`, the agent-written tools and the `agent-written` prompt section. It is selected last; the host's `instructions` become the first section (`host-instructions`) of `agent.<id>`, because Pi renders native `instructions` after every extension section.
- `.agent/AGENTS.md` is rendered by that section on every request through the request's environment, labelled as agent-written and capped at `MAX_AGENT_INSTRUCTIONS` (16,000) characters.
- `.agent/tools/<name>.json` is `{ name, description, parameters, run }`: `name` snake_case and not one of the agent's other tools, `parameters` a JSON Schema with `"type": "object"`, `run` one command line; a path under `.agent/` that `run` names must exist. Each becomes a native `ToolRegistration` (through `jsonSchemaTool`, so Pi refuses arguments that do not match `parameters` before `run` starts) whose `execute` runs `run` through the call's own `ExecutionEnv.exec` (the same provider instance as the files it was read from), with the arguments as one line of JSON on standard input (a quoted here-document); the output is the result and a non-zero exit is an error.
- `reload` (and `DefinedAgent.reload(env, context)`, which a host calls on open and for the person's `/reload`) reads `.agent/` through the given environment's `FileSystem`, rebuilds the extension and calls the native `registry.install()` in every registry `install` was given (same name: replaced in place). Reloads are serialised. The report (`SelfEvolutionReport`, its `text` is the tool result) names tools added, changed and removed, the agent's skills, the instructions and every load error (invalid JSON, schema, missing script, name conflict, unreadable file). A reload never imports or evaluates anything. Without `exec` the tools are reported unavailable and skipped; instructions and skills still load.
- Choices where the plan was silent: the folder is relative to the environment's working directory; there is no separate trust setting, approval or sandbox (isolation is where `exec` runs; hosts that want approval use the existing gate); `registry.uninstall()` is not needed because replacing the one extension removes deleted tools; an agent-written skill or tool that collides with a host one is refused, not shadowing it.

| ID | Law | Structural check | Runtime proof |
| --- | --- | --- | --- |
| SELF-1 | Opt-in. Without `selfEvolving: true` nothing reads `.agent/`, and no `reload` tool or agent-written prompt section exists. | Prompt assembly test in `test/packages/agent.test.mjs`: without the option the same `.agent/AGENTS.md` is never shown and the native instructions stay last. | Studio journey `self-evolution`: a subagent (no option) over the same workspace has neither. |
| SELF-2 | Never imported into the host. Agent-written tools execute only through the conversation's `ExecutionEnv`; no `import()`/`eval`/`Function` of workspace content in library or host code. | `npm run check` (`scripts/check-pi-boundary.mjs`, mutants in `test/pi-boundary.test.mjs`) over `packages/` and `examples/`. | Journey: a tool printing its environment on the virtual variant sees none of the host's variables. |

### Question notification recovery

External channel question notifications record success after `adapter.send` resolves. A restart retries an unacknowledged notification with the same assistant-entry-bound question ID. A crash after the external send but before the native acknowledgement can duplicate the notification; this is at-least-once delivery. The adapter may deduplicate that stable ID. A local success record does not prove that a person read the message.


## Target-bound viewer commands

`@hachej/boring-agent/presentation` exports `createPresentationTool`. It returns an ordinary native `ToolRegistration`; install it through the host's native extension/registry. Select this subpath with the optional `@hachej/boring-ui-kit` peer installed. The adapter imports UI contracts only, with no controller or renderer runtime.

Bind one `PresentationCommand` and its captured `ViewerTarget`. The target and parsed command input must be structured-cloneable data. Authorization receives a separate input/target copy, so its asynchronous work cannot change the command that executes. The adapter snapshots it at construction, so later calls never switch to whichever viewer is currently focused. Commands retain responsibility for checking resource, buffer, mount, projection, expiry and read-only state at their actual effect. A replaced editor can therefore refuse an old tool as stale or unavailable.

The host supplies:

- Native `parameters` for model arguments. Pi validates them before execution.
- `prepareInput`, which maps those arguments to command input, including a host-controlled deadline. The command's parser validates the mapped input.
- `authorize`, which checks the input and captured target against the actual native invocation and current host policy on every call. Target metadata is not permission.
- `formatResult`, which explicitly chooses the native result content/details. Inspection can contain private buffer text or resource references; project only what this conversation may retain. Refused commands always produce `isError: true`.

```ts
const navigate = createPresentationTool({
  name: 'navigate_notes',
  description: 'Navigate the bound notes viewer',
  parameters: Type.Object({ index: Type.Integer({ minimum: 0 }) }),
  command: mounted.revealHeading,
  target: capturedTarget,
  prepareInput: ({ index }) => ({ index, expiresAt: Date.now() + 5000 }),
  authorize: (_input, _target, api, context) => canNavigate(api.conversationId, context),
  formatResult: result => ({ output: [{ type: 'text', text: JSON.stringify({ kind: result.kind }) }] }),
});
```

Here `Type` is Pi AI's native schema builder, and `mounted`, `capturedTarget` and `canNavigate` belong to the host. The adapter passes native cancellation to the command and fixes replay to `unsafe`: an interrupted presentation call cannot safely be redirected or repeated. It acquires no controller, provider or Harness and owns none of their cleanup.

This is direct in-process binding. A server cannot manipulate a remote browser through this adapter alone. The optional [canvas host recipe](../../docs/architecture/CANVAS.md#authenticated-remote-presentation-recipe) supplies authenticated selection/proposal delivery to a mounted canvas. Other viewer transports and deployment identity remain separate work. Presentation/proposal results are not publication receipts or human approval.

## Structured actions

`@hachej/boring-agent/actions` provides `withActionModels(models, { resolve })`, an optional adapter at the public `HarnessOptions.models` seam. A host decision admits one structured extraction; its single validated tool call is executed by Pi. The next native generation renders a template from the actual tool result, without contacting an LLM. Ambiguous requests return to the full model. No extra harness, tool dispatcher or durable journal is created.

```ts
import { ACTION_PROVIDER, withActionModels } from '@hachej/boring-agent/actions';

const actionModels = withActionModels(admittedModels, {
  resolve: id => id === 'notes' ? {
    model: fullModel,
    extraction: { model: extractionModel, instructions: 'Extract one new note.', tool: noteTool },
    decide: async ({ message, history, signal }) => decideNote({ message, history, signal }),
    reply: 'Saved {note.title}.',
    uncertainReply: 'The outcome is uncertain. Check before retrying.',
  } : undefined,
});
// Pass actionModels as the models option when the host opens its native Harness.
await conversation.configure({ model: { provider: ACTION_PROVIDER, modelId: 'notes' } }, context);
```

`admittedModels` is the host's existing native Models, including its provider authentication and budget wrappers. `noteTool` is a native tool declaration, already installed and allowed in the conversation. The extraction schema may be stricter than that tool's schema; both are checked without coercion before returning a call. No commercial provider, API key, subscription or Jev client is embedded in the package. The host's `decide` adapts its chosen decision service; only literal `true` admits extraction. The callback gets native prior messages so the host can choose and bound the authorized decision context. Extraction receives only the current text input.

The default decision deadline is 400 ms and the input cap is 1,500 characters; `decisionTimeoutMs` and `maxInputCharacters` override them. Decision failure/timeout, non-text input, missing current tool, malformed/multiple extraction calls or extraction refusal return to the full model. The decision receives an abort signal; an uncooperative service may finish later, but its result cannot start extraction. Native compaction uses `completeSimple` with a tool-free summarization context, which delegates to the full model. Explicit deferred requests also use the full model; polling and cancellation retain the underlying provider. Missing action definitions or full models return the native unavailable-model result. Unselected models and native registry capabilities remain available.

Reply placeholders such as `{note.title}` accept actual strings, finite numbers and string arrays (joined by newline). Missing output, a failed tool or unreadable result produces `uncertainReply`, never a blind replay of a possible mutation. `rejectedWithoutEffect(result)` may opt into full-model handling only when the host can prove an atomic rejection; a throwing predicate leaves the outcome uncertain. Tools still own permission checks and durable idempotent receipts; the adapter cannot make external writes transactional. Install the adapter outside the metered Models so real extraction and fallback requests retain admission. Synthetic replies have zero usage; failed extraction usage needs host request metering because only the final fallback message enters Pi's transcript.

Hosts must explicitly configure existing conversations when adopting this virtual model; deployment alone does not change their persisted selection. Keep the action's tool and result contract compatible while native work is pending. Changing definitions during an outstanding action is not a version-pinning guarantee.

Evidence: `node --test test/packages/agent-actions.test.mjs` runs the public package through a native Harness, SQLite reopen, native tool gates and scripted models. `npm run test:definitions-consumer -- --actions` repeats these tests and checks strict installed declarations. Real-model speed and decision accuracy remain consumer evals, not claims of these scripted tests.
